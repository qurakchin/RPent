# a_1 仓库结构、组件边界与安装
> 状态：草案｜基线 `01e9cb3`｜最后更新 2026-11-14

> 目录决定依赖方向，文件名决定角色，骨架决定评审单位；依赖跟着组件走，环境按具名配方组装，安装留下指纹。
>
> 前置阅读：[a_global](a_global.md) 2.1 节（名字与路径）、R1/R2/R7/R8/R10/R12；[a_5](a_5_精简机器人接入.md) 的切片构成；[a_3](a_3_抽出共享工具族.md) 的工具包边界。
>
> 本文只改组织方式与依赖边界，不改运行语义。搬移和改名必须行为不变；切片文件的删除（`env_client.py` 等）随 a_5 的迁移发生，不在本文的结构批次里做。

## 1. 问题背景

### 1.1 同类组件没有共同形状

七个切片里，相同角色出现多种文件名或载体：

| 角色 | 现状 | 目标（a_5） |
|---|---|---|
| 环境接入 | 7/7 有 `env_client.py` + `env_server.py`；另有 3 个 `rlinf_env.py`、2 个 `rpent_env.py`；2 个把原生逻辑直接写在 `env_server.py` | `adapter.py`；client/facade 在核心 |
| 工具调度 | 7/7 有 `toolkit.py`；2 个类属性声明式、5 个 `_register_<name>_tools()` 命令式 | 由 `config.py` 声明工具族，无 `toolkit.py` |
| 工具声明 | 7/7 有 `tools.py`，4/7 另有 `primitives.py`，职责重叠 | 工具族 + `native_tools.py` |
| Prompt | 7/7 有 `prompt_bundle.py`；`prompts/` 有三种拆分（按调用模式拆，不按内容拆） | `prompts/domain.py` |
| 机器人描述 | 7/7 有 `robot_spec.py`（286–746 行）；包入口 2 个惰性、5 个急切 | `spec.py` ≤80 行，入口一律惰性 |
| 技能绑定 | `vla_client/server`、`wam_client`、`awomo05_client/server`、`vpp2_client/server`、`vla_test.py`、`perception.py`，6 种写法 | `skills/<skill>.py` |
| 任务选择 | `tasks.py`（4）、`suites.py`（1）、`eval/*.json`（2） | `config.py` |
| 评测 | `eval/`（2）、`evaluation.py`（1） | `evaluation/` |

核心里也有同样的问题：`rpent/robots/components/`（29 个文件、4.4k 行）同时放环境基类、动作模型基类和具体模型服务，目录名不再说明它是什么；8 个模型服务中 3 个是包、5 个平铺。核心其余部分对它的引用为 0，模型能力本来就不是核心依赖。`calibration_tools/`、`requirements/` 和根脚本没有设计归属。

### 1.2 安装：依赖归属与隔离缺失

一个 `pyproject.toml`（309 行）装下所有平台：14 个 extra（约 115 行），7 个通过 `rpent[...]` 继承其他 extra，15 对 `[tool.uv] conflicts`。extras 能表达「多装一组」，不能表达「这两组不能一起装」或「这个组件应该在另一个环境里」。

| 冲突 | 具体表现 |
|---|---|
| 同名包不同来源 | `rlinf` 在常规 extra 里是 `RLinf/RLinf@release/v0.4`，在 `robodojo-sim` 里是 `littleZ05/RLinf@rpent/robodojo` |
| 同一个包多个 pin | torch：OpenPI 2.7.1、RoboDojo override 2.7.0、CUROBO 构建 2.8.0；transformers：OpenPI 4.53.2 与 Molmo `>=4.57` |
| 仿真器互斥 | LIBERO 要 `mujoco==3.3.0`，YAM 要 `mujoco>=3.2,<4`；Franka 要 `gymnasium==0.29.1` 和 `numpy<2` |
| 必须手工 override | `requirements/robodojo-override.txt` 覆盖 8 个 pin，要手工附加到安装命令 |
| 冲突只写在注释里 | `molmo` 的注释说明与 OpenPI 冲突，但 `conflicts` 只列了 `robotwin × molmo` |

安装知识分散：中英文文档 16 个页面共 26 处 `uv pip install -e ".[...]"`；`tests/e2e_tests/run_gpu_suite.sh` 把 target → extra → Python 版本的映射写在脚本里；`toolkits*` 被 `packages.find` 排除；没有 lock、安装清单，`run.json` 也不记录环境。

## 2. 根因

1. **封装单位是机器人，目录就按机器人复制。** 第二个切片出现时，默认动作是复制邻近切片；`add_robot.rst` 还明说「可以把它们放在一个 `toolkit.py` 里」，骨架从规定变成了建议。
2. **没有「角色」这个概念。** 只有「文件放哪」的约定，同名文件可以承担完全不同的责任，同一角色也可以有多个名字。
3. **依赖的归属错了。** 依赖属于组件，现在都堆在根 `pyproject.toml`，再用 extra 当命名空间；extra 没有导入探针、没有 Python/平台范围，不能单独锁，也不能表达运行时位置。
4. **环境没有一等表达，安装不是产物。** 哪些组件能一起装只存在于 `conflicts`、CI 脚本和文档文字里；装完没有清单和 doctor，漂移只能靠运行时异常发现，缺依赖时看到的是裸 `ModuleNotFoundError`。

## 3. 优秀参考与原则

| 参考 | 做法 | 借鉴 |
|---|---|---|
| URA `docs/development.md` | `Owns / Keep out` 表规定每个目录负责什么、禁止放什么 | 顶层目录登记 owner |
| RPent GPU suite | 每个 target 一个干净 venv，装完跑 `uv pip check` | 已有正确做法，变成配方和 CI 契约 |
| Molmo 独立解释器 + RPC | 冲突的模型栈放另一个环境，用 endpoint 连接 | 「外部环境」是正式放置方式 |
| uv `conflicts`、PEP 735 dependency groups | 互斥显式声明；dev/test 依赖与运行时分开 | 冲突由安装前检查消费；`test` 不再是 extra |
| RLinf `requirements/embodied/` | 按环境和模型组织依赖文件 | 按组件组织；**不照搬** 4700 行的 `install.sh` |

**原则**：

- 文件名即角色；同类组件同骨架，可选角色缺席就省略，不放空文件；
- 依赖单向：`robots/` → `toolkits/`、`capabilities/` → `rpent/`；核心按名字发现组件，从不静态 import 它们；
- 依赖跟着组件走，一个版本约束只有一个所有者；
- 环境是具名配方，不是任意组合；核心在最小环境里可导入、可发现机器人、可显示 `--help`；
- 结构规则必须可机器检查，否则会退化；不引入第二套包管理器，继续用 `uv`。

## 4. 目标设计

### 4.1 顶层目录与 owner

| 顶层 | 角色 | owner | 不允许放 |
|---|---|---|---|
| `rpent/` | 核心：契约、调度、共享实现 | a_global 第 3 节 | 机器人名、平台分支、可选重依赖 |
| `robots/` | 切片：原生翻译与差异化功能 | a_5 | 通用工具、通用 prompt、产物布局 |
| `toolkits/` | 工具包：重实现 + 独立评估 | a_3 | 切片专用逻辑 |
| `capabilities/` | 模型服务与 `_base/` 基类 | a_3 4.7 | 机器人名、判据 |
| `envs/` | 环境配方、依赖组件清单（`deps/`）与依赖锁 | a_1 | Python 源码 |
| `tests/` | 契约、故障注入、parity、e2e | a_9 | 业务实现 |
| `docs/` | 用户、开发与设计文档 | a_0 | 运行产物 |
| `scripts/` | 仓库级检查与发布脚本 | a_9 | 业务逻辑 |

`calibration_tools/` 按机器人拆进 `robots/<name>/calibration/`：现有脚本服务 `dual_franka` 的基座相机标定（通过 libfranka 读取 Franka 状态），单 `franka` 的标定仍走 ROS easy_handeye，不需要这批脚本。`requirements/robodojo-override.txt` 移进对应组件目录的 `requirements/`。新增顶层目录必须先改本表。

根文件白名单：`pyproject.toml`、`README*`、`CONTRIBUTING*`、`LICENSE`、`AGENTS.md`、`CLAUDE.md`（一行 `@AGENTS.md`）、`.gitignore`、`.pre-commit-config.yaml`。根脚本 `shadow-pr.sh`、`sync_upstream.sh` 移到 `scripts/`；基线里误提交的 `.coverage` 删除并加入 `.gitignore`。隐藏目录（`.github/`、`.agents/`、`.claude/`）属于工具配置，不登记 owner。

`rpent/robots/components/` 拆成三处：环境基类 → `rpent/env/`（a_5）；动作模型基类（`am_client_base`、`am_facade_base`、`am_contracts`、`am_runtime`、`action_spec`）→ `capabilities/_base/`；具体模型服务 → `capabilities/<name>/`。`rpent.robots.components` 保留一个 release 的转发模块。

### 4.2 组件骨架与依赖清单

**机器人切片 `robots/<name>/`**（构成与行数见 a_5 4.5）：

```text
component.toml   __init__.py   spec.py   config.py   adapter.py   prompts/{__init__,domain}.py   # 必需
skills/   native_tools.py   memory.py   flash/   evaluation/   guides/   configs/   calibration/   requirements/   # 可选
```

`calibration/` 只放在服务真机的切片，存标定采集与求解脚本；`requirements/` 存组件自己的 override 文件，文件名由 4.4 的 `overrides` 列出。两者都是可选角色，缺席时不建空目录。

**工具包 `toolkits/<name>/`**（a_3 4.3）：

```text
component.toml   __init__.py   tool.py   core.py   observation.py   evaluation/      # 必需
config.py   prompts.py   requirements/                                               # 可选
```

**模型服务 `capabilities/<name>/`**（a_3 4.7）：

```text
component.toml   __init__.py   server.py   config.py   README.md                       # 必需
client.py   adapter/encode.py   adapter/decode.py   requirements/                       # 可选
```

**依赖组件 `envs/deps/<name>.toml`**：只有这一份清单，没有目录、Python 源码或 `__init__.py`；`kind = "deps"`，字段与 4.4 相同，但不写 `placement` 和 `probe`（没有可导入模块，`rpent-env doctor` 跳过探针），随引用它的组件放置。它只用于**被两个以上组件 `requires`、本身不提供服务或代码**的第三方依赖（R7），让这组依赖的版本约束有唯一所有者。首批只有 `rlinf`（LIBERO、RoboTwin、RoboCasa、Franka 等都 `requires` 它）；只剩一个使用方时，依赖写回那个组件自己的 `dependencies`，清单删除。

角色名就是上面这些文件名。切片和组件里的旧名在迁移完成后禁止出现：`robot_spec.py`、`prompt_bundle.py`、`env_client.py`、`env_server.py`、`toolkit.py`、`tools.py`、`primitives.py`、`rlinf_env.py`、`rpent_env.py`、`runtime_config.py`、`tasks.py`、`suites.py`、`eval/`。核心的 `rpent/robots/robot_spec.py`、`rpent/tools/toolkit.py`、`rpent/prompt/common.py` 不是切片角色，保留原名，不按切片角色改名。`runtime_config.py` 的两种含义分别归入组件自己的 `config.py`（运行期配置）和 `capabilities/_base/runtime.py`（模型运行时选择）。类名 `CommonTools` 在同一迁移中改名为 `FileTools`，`rpent/tools/common.py` 清空后删除。

切片入口一律惰性，避免一个切片的缺失依赖拖垮全仓的机器人发现和 CLI help：

```python
def __getattr__(name: str):
    if name == "get_robot_spec":
        from .spec import get_robot_spec
        return get_robot_spec
    raise AttributeError(name)
```

### 4.3 复用判定

复用规则以 R1、R7 为准，这里只补一条执行顺序：

1. **骨架复用无条件**：同类组件用同一套文件角色，与代码是否复用无关；
2. **代码复用看 R7**：两个以上真实使用方，且契约和失败语义一致，就抽到 `rpent/` 或 `toolkits/`；
3. **不满足时保留两份**，并在两边写明是原生差异还是语义不同。复制后只改参数不算差异，按 R1 处理。

### 4.4 组件清单 `component.toml`

```toml
schema = 1
name = "libero"
kind = "robot"                    # robot | toolkit | capability | deps
probe = "robots.libero"           # 导入探针，doctor 用
python = ">=3.10,<3.13"
platforms = ["linux-x86_64"]
requires = ["rlinf", "openpi", "sam3"]      # 依赖的其他组件；闭包由安装器计算
env_conflicts = ["franka", "robotwin", "robodojo"]
placement = ["in-env"]            # 允许的放置方式（集合）：in-env | external-env | remote
dependencies = [
  "rpent-libero @ git+https://github.com/RLinf/LIBERO.git@rpent",
  "mujoco==3.3.0",
]
overrides = []                    # 组件目录内的 override 文件，如 ["requirements/robodojo-override.txt"]，文件开头写明原因

[optional]
pro = ["rpent-liberopro @ git+https://github.com/RLinf/LIBERO-PRO.git@rpent"]
plus = ["rlinf-liberoplus", "h5py"]
```

- **只声明直接依赖**：`libero` 需要 OpenPI 就写 `requires = ["openpi"]`，不抄 OpenPI 的包；
- **版本约束只有一个所有者**：torch 的 pin 属于 `openpi`，`sam3` 只写 `torch`；同一环境里出现两个不同的 pin，`rpent-env check` 报错；
- **冲突写一次**：检查器按对称闭包处理，两边都写但不一致时报错；
- **组件没有独立版本号**：组件版本就是「源码 commit + 清单 hash」；
- **共享能力按 R7 抽取**：只有一个消费者的依赖留在组件自己的 `dependencies` 里；
- **override 属于组件**：`overrides` 列出的每个路径都必须位于组件目录内，`rpent-env check` 校验文件存在；override 只用于 resolver 无法表达的 pin，原因写在文件开头。

### 4.5 环境配方 `envs/<profile>.toml`

```toml
schema = 1
name = "libero-pro"
python = "3.11"
platform = "linux-x86_64"
lock = "envs/locks/libero-pro.lock"

[components.libero]
placement = "in-env"                # 本配方的选择，必须在组件 placement 集合内
variant = "pro"

[components.sam3]
placement = "in-env"

[components.molmo]
placement = "external-env"
profile = "molmo-server"
```

- **受支持目标只走具名配方**；需要新组合就加一个配方并评审；
- **配方名不与组件同名**：带 `-sim`、`-real`、`-pro`、`-server` 这类后缀，或叫 `minimal`、`dev`；
- **Python 和平台写到 minor**，不让 resolver 去猜；
- **`in-env` 组件检查 `env_conflicts`**；两个互斥组件只有一个放到 `external-env` 时才能同配方；外部环境有自己的配方，主配方只引用其 endpoint。

现有 extra 的去向：`test` → `dev` dependency group；`sam3` / `openpi` / `molmo` → capability 组件（`molmo` 只有 `molmo-server` 外部配方）；`rlinf` → 依赖组件；`libero*` → `libero` 组件加三个配方；`franka` / `yam` / `robocasa` / `robotwin` / `robodojo` → 同名组件加配方；`robodojo-sim` 只有 `robodojo` 一个使用方，它的 RLinf fork 和仿真运行时写进 `robodojo` 组件自己的 `dependencies`，`robodojo` 声明 `env_conflicts = ["rlinf"]`；`flywheel` → LIBERO 组件的可选组。

### 4.6 安装器 `rpent-env` 与检查

新增 console script `rpent-env`（`rpent/cli/env.py`）：

| 命令 | 作用 |
|---|---|
| `rpent-env list` | 列出组件和配方 |
| `rpent-env check <profile>\|--all` | 清单、闭包、冲突、重复 pin、Python/平台检查；不下载依赖；`--resolve` 再用 `uv pip compile` 确认 |
| `rpent-env install <profile>` | 创建或复用 venv，按依赖文件安装，跑探针和 `uv pip check`，全部通过后写安装指纹；`--component <name>` 只用于开发诊断 |
| `rpent-env lock <profile>\|--all [--check]` | 生成或校验依赖锁 |
| `rpent-env doctor` | 校验当前 venv：Python、平台、探针、`uv pip check`、外部 endpoint，以及指纹漂移 |

安装指纹 `<venv>/rpent-install.json` 记录配方、`source_commit`、各组件清单 hash、`requirements_sha256`（输入）和 `freeze_sha256`（安装结果）；`run.json` 记录 `profile` 与指纹 hash（a_8）。没有指纹的环境（兼容期的 `pip install -e .[<extra>]`）照常运行，`run.json` 里写 `null`。

缺依赖时报组件名和配方，不报裸 `ImportError`：

```python
from rpent.install import require
torch = require("sam3", "torch")   # 失败：组件 sam3 未安装；包含它的配方：libero-pro、robotwin-sim
```

**兼容期**：根 `pyproject.toml` 的 extras 由 `scripts/gen_extras.py` 从清单生成，保留一个 release 后删除。

**`check_layout` 的结构规则**（实现见 a_9 4.4）：

| 编号 | 规则 | 级别 |
|---|---|---|
| K1 | 顶层的非隐藏目录只允许 4.1 表中的目录；根文件只允许 4.1 的白名单；隐藏目录豁免 | warning → error（S1 上线，S3 转 error） |
| K2 | 每个组件目录有 `component.toml`，并有 4.2 的必需文件；`envs/deps/*.toml` 的 `kind` 必须是 `deps`，且至少被两个组件 `requires`；`overrides` 列出的文件位于组件目录内且存在 | error（S3 起） |
| K3 | 4.2 的旧名不得新增；迁移完成的切片里不得存在 | error（S3 起） |
| K4 | import 方向：`rpent/` 不 import `robots/`、`toolkits/`、`capabilities/`；`toolkits/`、`capabilities/` 不 import `robots/`；切片之间、工具包之间、模型服务之间不互相 import | warning → error（S1 上线，S3 转 error） |
| K5 | 核心里不出现机器人名、benchmark 名（R8） | warning → error（S1 上线，S3 转 error） |
| K6 | 切片 `__init__.py` 只有惰性 `__getattr__` | error（S2 起） |
| K7 | 切片里的 `spec.py` >80 行、`adapter.py` >400 行、`native_tools.py` >100 行 | warning |

级别与批次一致：S1 只启用 K1、K4、K5 并以 warning 运行；S2 随入口惰性化启用 K6（error）；S3 启用 K2、K3，并把 K1–K5 全部转为 error。K7 保持 warning。

最小环境测试：只装核心和 `dev`，验证 `import rpent`、`rpent --help`、`enumerate_robots()` 可用。

### 4.7 文档与 CI 收敛

- 新增一页 `installation`，按配方写安装；机器人页面只保留平台准备（GPU、资产、checkpoint），安装命令统一为 `rpent-env install <profile>`；
- PR 跑 `rpent-env check --all`、`check_layout` 和最小环境单测；nightly 对每个受支持配方做一次 fresh venv 安装 + doctor；GPU e2e 脚本改为读配方；release 前 `rpent-env lock --all --check` 必须通过；
- P5 删除生成的 extras 时，`scripts/check_docs.py` 增加安装命令规则：文档中的安装命令只允许 `rpent-env install <profile>`，且 `<profile>` 必须存在于 `envs/`；兼容期内 `pip install -e .[<extra>]` 仍按现有 extras 校验。

## 5. 目标与非目标

**目标**

- 每个顶层目录有 owner；同一角色在七个切片里只有一个文件名；
- 根 `pyproject.toml` 只保留核心依赖；每个组件有 `component.toml`；
- 每个受支持目标有具名配方、依赖锁和 fresh-install 记录；冲突显式、对称、安装前可检查；
- 缺少组件时的错误信息直接给出配方；每次运行都能从 `run.json` 追到安装指纹。

**非目标**

- 不为统一而统一：只改与 a_5 目标冲突或已有第二种写法的角色；
- 不改变 RPC 协议、工具名、返回字段和 prompt 文案（这些由各主题文档负责）；
- 不引入元类、插件系统或第三方组件发现；不拆成多个 PyPI 发行包，也不引入组件级版本号；
- 不引入 conda、pixi 或第二套 resolver；不在运行时 `pip install` 或下载权重；
- 不要求有 VCS 依赖的配方带 hash 锁，记录 commit 和冻结版本即可；
- 不用安装检查替代运行时 e2e。

## 6. 如何实施

结构批次只搬移、改名、补骨架，不改运行逻辑；安装批次与之并行。

| 阶段 | 内容 | 验收 |
|---|---|---|

## 8. 风险

| 风险 | 对策 |
|---|---|
| 大规模改名制造 review 噪音 | S2 只做机械改名，单独 PR，不夹带逻辑；用 `git mv` 保留历史 |
| 目录搬迁打断进行中的 PR | 按切片串行；转发模块保留一个 release |
| 清单与实际 import 漂移 | 组件探针 + 每个配方的 fresh-install 测试；新增依赖必须同时改清单 |
| 配方数量膨胀 | 只接受具名配方；新增配方需要 CI 记录和评审 |
| 锁文件频繁变化 | 只在组件改动或 release 时重锁；锁 diff 进 PR 评审 |
| override 掩盖真实不兼容 | override 写原因和影响范围；装完仍要跑对应 target 的 e2e |
| 安装通过被误当成真机可用 | 安装检查只算 CPU 证据，真机证据按 a_0 分级记录 |
