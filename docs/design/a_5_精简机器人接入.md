# a_5 精简机器人接入
> 状态：草案｜基线 `01e9cb3`｜最后更新 2026-11-13

> 用「语义契约 + adapter」取代切片里的三层 RPC 拷贝，让切片只做原生翻译。
>
> 前置阅读：[a_global](a_global.md) 第 3 节、R1/R2/R8；组件依赖与环境配方见 [a_1](a_1_隔离组件依赖与安装.md)。

## 1. 问题背景

在 RPent 里接一个新机器人，要把整条栈重写一遍：仿真胶水、环境 RPC、观测解析、模型可见的工具、prompt、进程拉起、CLI、VLA 客户端。

| 基线（口径见 a_global 5.1） | RPent | URA |
|---|---|---|
| 核心 | `rpent/` 18.1k 行 | 27.6k 行 |
| 机器人 / 集成 | `robots/` 35.7k 行，占 66%，共 7 个切片 | `integrations/` 9.6k 行，占 26%，共 12 个集成 |
| 单个切片 | 3.5k–7.4k 行 | 19–2314 行，多数不超过 1.2k |

同一个仿真（RoboTwin）的对照：

| | RPent `robots/robotwin/`（约 4.0k 行） | URA `integrations/robotwin/`（227 行） |
|---|---|---|
| 仿真接入 | `rlinf_env` 400 + `env_server` 398 + `env_client` 223 + `robot_spec` 746 | adapter 146 + server 81 |
| 工具 | `tools` 427 + `primitives` 528 + `toolkit` 358，共 12 个手写 `@tool` | 0 行，由共享工具族按能力装配 |
| prompt | 约 385 行手写 | 0 行手写 |

口径差异：URA 的 RoboTwin 只支持 Direct 模式，RPent 还带了 LingBot VLA 和记忆。但只比「把仿真接进来」这一层，差距也在 7 倍以上。

## 2. 根因

**抽象的轴选错了。** RPent 以机器人为封装单位，每个切片都是从 RPC 到 prompt 的一条垂直栈；URA 以能力为封装单位，水平分层，每层只有一个所有者。在接入层面，这个问题表现为四点：

1. **契约的形状不对。** `BaseEnvFacade._register_rpc()` 暴露的是 gym 形状的 `env.step(action)` 和 `env.chunk_step`，参数是原生 action 向量，方法集合也由各切片自己定义。结果是工具层必须懂每个仿真的 action 语义，同一个接口要写三遍：`rlinf_env` 实现，`env_server` 去 batch 并注册，`env_client` 再包一层类型。成本是「切片数 × 3 层」。
2. **包错了层。** RLinf 的 Env 是为训练设计的，有 `num_envs`、批量 tensor、auto-reset、seed 预跑。切片继承它之后，还得逐项抵消这些训练特性：修正 seed 预跑、按任务名补齐评测器的私有状态、`step_lim` 三级 fallback、`_strip_single_env_*` 去 batch 维。「仿真本身代码量大」主要就来自这一层。如果只定义契约、不动这一层，这些冗余会原样搬进 adapter。
3. **观测没有归一化。** 原生 obs 字典原样透传，于是每个切片的工具都要自己理解原生格式。例如 RoboTwin 的「EE 参考点在 TCP 后方 0.12 m」写在了工具和 prompt 里，PR #340 的代码模式 prompt 又写了一遍；URA 只在 adapter 里换算一次。
4. **进程拉起和 CLI 逐切片复制。** `robot_spec.py` 有 286–746 行，大部分是参数注册、找端口、spawn、等待就绪、分配 CUDA。`_spawn_sam3_server` 有 3 份逐字相同的拷贝。核心里还有平台表（`am_runtime.py` 的 `PLATFORM_VLA_BACKENDS`），新增机器人时要改核心代码。

工具、prompt、产物方面的重复分别在 a_3、a_2、a_8 处理。

## 3. 优秀参考、原则与结构

URA 的接入只需要三样东西：

| 组成 | URA 的做法 | RPent 借鉴什么 |
|---|---|---|
| 语义契约 | `EnvironmentDescription / EnvironmentState / PoseCommand / StepReceipt / CapturedObservation` | 契约描述**语义命令**，不描述原生 action |
| 通用 server/client | `serve_episode` + `build_router` + `EnvironmentClient`，全包一份 | facade 和 client 由核心提供，切片不实现 |
| adapter | 只处理原生差异：EE 偏移、夹爪开度反算、外参 3×4 补成 4×4 再求逆；不支持的能力抛 `RequestRejected` | adapter 只翻译，不抹平仿真差异 |
| 部署声明 | `deployment.toml` + pydantic `config_model` | 组件声明加通用的 starter |

由此得到本主题的原则（对应 a_global 的 R1/R2/R8）：

- 契约稳定、语义化；
- adapter 允许写长，但只能包含原生差异；
- 能力由 adapter 声明，工具和 prompt 从能力推导（见 a_3、a_2）；
- 进程由核心拉起，切片只做声明。

## 4. 目标设计

### 4.1 环境契约：`rpent/env/contracts.py`

```python
# get_env_meta() 返回的 dict（沿用现有 facade 方法）：
# arms: tuple[ArmDesc, ...]            # name, control_frame, grasp_site, rotation_radius_m
# cameras: tuple[CameraDesc, ...]      # name, has_depth, calibrated
# gripper_opening_model: Literal["normalized", "metric"]
# control_modes: frozenset[str]        # 子集 of {"pose", "joints", "native"}
# control_frequency_hz: float
# max_episode_steps: int | None
# contract_version: int
# metadata: dict                       # 原生 revision、embodiment 等

@dataclass(frozen=True)
class EnvSnapshot:
    arms: dict[str, ArmState]            # control_pose（grasp site）、joints、gripper∈[0,1]
    state_version: int
    native_steps: int
    episode_over: bool                   # 只表示结束，不表示成功（a_7）

# obs dict（沿用现有 reset() / step() 的返回）：
# state_version: int
# frames: dict[str, CameraFrame]       # rgb, depth[m], K, T_world_from_optical
# state: EnvSnapshot
```

- **命令**：pose action（可同时给多条臂）、joint action、native chunk，共三类；沿用现有 `action` / `chunk_step` 的术语。
- **回执**：写命令统一返回 `ToolResult`，语义见 a_6。回执字段随 `ToolResult` 一起维护，避免以后为它再改一次协议。
- **控制点**：所有位姿都指向 `grasp_site`。像「EE 在 TCP 后方 0.12 m」这类原生差异，只在 adapter 里换算一次。

### 4.2 adapter 与通用 facade / client

```python
# adapter 由切片现有的 env 类实现：RoboTwinAgentEnv / RoboDojoAgentEnv /
# YamAgentEnv / RPentFrankaEnv / RPentDualFrankaEnv / ...
# 方法沿用现有基类：
#   get_env_meta() -> dict
#   reset() / step(flat_action) -> obs
#   chunk_step(flat_actions, return_all_frames=False) -> obs
#   get_camera_meta(camera_name) / render_camera(camera_name) -> dict / image
#   get_task_language() -> str | None
#   finish() -> dict                       # 真值只进产物，不回给模型（a_7）
#   close() -> None
```

- 不支持的控制模式抛 `RpcError(code="rejected")`，并且不在 `control_modes` 里声明；
- `BaseEnvFacade` 把语义命令路由到 adapter，负责生命周期、协议校验和账本（a_6）；
- `BaseEnvClient` 全仓只有一份，切片不再写 `env_client.py`；
- 传输沿用现有 RPC（HTTP JSON 或 socket），**不改成 FastAPI**。

### 4.3 adapter 包装什么：先写决策记录

| 方案 | 做法 | 适用场景 | 代价 |
|---|---|---|---|
| **(a) 包装上游原生仿真** | 钉死 revision，setup 复用上游的 eval 入口 | 上游有可用的 eval 入口 | 每个仿真要自己找入口 |
| **(b) 单环境 agent 视图** | 在核心里**只写一次**单环境处理（`BaseEnvClient` 内部）：`num_envs=1` 去 batch、seed 对齐、通用的 `chunk_step` 和相机查询 | 多个仿真共用 RLinf Env | 依赖 RLinf 的内部行为，需要钉住 revision |

选型依据：

- 是否需要跨仓库改动；
- 上游 revision 是否可控；
- 能覆盖多少个仿真；
- 真机 `RealWorldEnv` 能否共用。

无论选哪个，RLinf 的 VLA 推理和真机 `RealWorldEnv` 都照常复用。要停止的只是「每个切片继承训练 Env，再改写它的行为」。

### 4.4 进程拉起：沿用 `RobotSpec.init_runtime`

现有 `rpent/robots/runtime.py` 的 `try_spawn_server` / `try_wait_server` / `stop_owned_daemons` 已经负责 spawn 或 attach、按顺序等待就绪、按逆序停止；`RobotSpec.init_runtime` 继续作为切片的入口。改造只把各切片重复的 `_spawn_*` 和 `_init_runtime` 收敛到这三个函数，不新增 starter 模块。CLI 参数由切片的 pydantic 配置模型生成，explore、memory 这类通用参数由核心统一注册。平台表下放到各切片的配置里。

### 4.5 切片的目标构成

| 组成 | 文件 | 行数目标（接入部分） |
|---|---|---|
| 组件清单：直接依赖、探针、Python/平台与冲突 | `component.toml` | 20–40（a_1，不计入 Python 行数） |
| adapter | `rlinf_env.py` / `rpent_env.py` | 250–400 |
| VLA/WAM client binding（含平台传输） | `skills/*.py` | 150–300（a_3） |
| 配置、能力声明、组件声明、判据阈值 | `config.py` | 100–200 |
| 领域 prompt | `prompts/domain.py` | 100–200（a_2） |
| 原生特有工具 | `native_tools.py`（可选） | ≤100 |

Flash、记忆策略 hook、benchmark 评测脚本、真机运营与安全逻辑属于差异化功能，单独计算（a_global 5.1）。

## 5. 目标与非目标

**目标**

- 新机器人只需提供 adapter、配置与能力声明、VLA/WAM client binding、领域 prompt，以及真正特有的工具；
- 接入部分 ≤1.2k 行，试点 RoboTwin ≤1.0k 行；
- 环境 client、facade 和单环境视图全仓各只有一份，核心里不出现机器人名。

**非目标**

- 不照搬 URA 的 FastAPI 服务化；
- 不造通用的仿真 DSL；adapter 不负责抹平仿真之间的差异；
- 不一次性重写，按 strangler 方式逐个切片迁移；
- 不削弱差异化能力：真机运营（`operator_control`、`hardware_ownership`、`servo`、`recovery`）、HIL、Flash、flywheel、分层记忆、Dashboard；
- 平台适配（`vla_client`、`vla_server`、`wam_client` 共约 660 行，已经继承核心基类）不当作副本删除，而是并入 VLA/WAM client binding（a_3）。

## 6. 如何实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0 定边界** | 把 R1/R2/R8 写进 `AGENTS.md`；新增 `env_client.py` 视为违规 | 规则合入，`check_layout` 以 warning 级别上线（a_9） |
| **P1 契约** | `contracts.py`、adapter、通用 `BaseEnvFacade` / `BaseEnvClient`，与 a_6 的回执同步落地 | RoboTwin 只靠 adapter 就能跑通一轮 Direct 动作，且不修改共享工具 |
| **P2 包装对象** | 写决策记录，在试点上落地 (a) 或 (b) | 切片里不再有 `rlinf_env.py`，或该文件 ≤150 行；adapter 里没有 seed 预跑修正、`step_lim` fallback、`_strip_single_env_*` |
| **P3 进程拉起** | `RobotSpec.init_runtime` + `runtime.py` 的三个函数 + 配置模型；平台表下放 | 切片里的 `robot_spec.py` 降为 ≤80 行的入口，或删除；切片中不再有端口分配和就绪轮询 |
| **P4 迁移其余切片** | 顺序：LIBERO → RoboCasa / RoboDojo → yam、franka、dual_franka | 每个切片的工具名、schema、feedback、finish 语义不变，parity 和冒烟测试通过 |

**试点用 RoboTwin**：两边都接过，URA 有 227 行的现成参照，并且没有真机风险。

**迁移开关**：`env_contract: legacy|v2`，按切片设置。旧路径保留到试点完成、并且又有一个切片通过 parity。任一切片的 parity 失败，只关闭该切片的开关，不影响其他切片。

## 8. 风险

| 风险 | 对策 |
|---|---|
| adapter 越写越长，吸收了本该由框架处理的差异 | 契约只描述语义命令和归一化观测；adapter 里的特殊处理必须注释说明是原生差异 |
| 包错层的问题在 adapter 里复现 | P2 的验收硬性检查抵消训练特性的代码；方案 (b) 的单环境视图只在一处实现 |
| 方案 (b) 依赖 RLinf 内部实现 | 钉住 RLinf revision，保留方案 (a) 作为回退；真机 `RealWorldEnv` 单独验证 |
| 行为漂移 | 工具 schema 快照 + parity + 现有测试全量回归 |
| 双路径并存时间过长 | 一次只推进一个切片；全系列不新增第二个迁移开关 |
| 真机回归 | 真机切片最后迁移；回执、锁存、operator 门控和 TTY 门控的行为必须保持一致 |
