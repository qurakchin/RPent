# a_9 建立验证护栏
> 状态：草案｜基线 `01e9cb3`｜最后更新 2026-11-14

> 把每条规则、每个验收条件都变成可执行的测试或 CI 检查，避免改造成果在后续 PR 中逐渐退化。
>
> 前置阅读：[a_global](a_global.md) 第 4、5 节。

## 1. 问题背景

RPent 的测试基础比 URA 好得多：基线有 97 个 `test_*.py`，分为 `unit_tests/` 和 `e2e_tests/`（覆盖 libero、robocasa、robodojo、robotwin、dual_franka）；CI 有 `unittest`、`pre-commit` 和 GPU e2e 三类 workflow。URA 的公开仓库没有测试文件，只有 `scripts/validation/`。这是 RPent 的相对优势，改造过程中必须保住。

问题在于，现有测试按模块生长，没有覆盖跨模块的契约：

| 本系列的约束 | 现状 |
|---|---|
| prompt 不丢关键约束（a_2） | 没有快照 |
| 结果四层、能力决定 schema（a_3） | 没有锁定 |
| 两种调用模式的结果一致（a_4） | PR #340 只有生命周期测试 |
| adapter 只做翻译、不继承训练 Env（a_5） | 没有一致性测试 |
| 重复请求不执行、超时后锁存（a_6） | 没有故障注入，只有 RoboDojo 和 dual_franka 各自的私有测试 |
| 评测模式下真值不可见（a_7） | 没有快照 |
| 产物布局与关联 ID（a_8） | 没有 schema 校验 |
| 迁移前后行为不变 | 只能人工冒烟 |

此外，CI 拦不住架构回退，例如切片里重新出现 `env_client.py` / `env_server.py`、核心代码里出现了机器人名、prompt 里重新写了参数说明。

本文负责可机器判定的部分；规则文本、证据格式和文档状态见 [a_0](a_0_建立文档纪律与评审闸门.md)；工具自身的质量评估见 [a_3](a_3_抽出共享工具族.md) 4.5。

## 2. 根因

1. **测试按模块组织，而不是按契约组织。** 例如没有一个共享测试来证明「任何 episode 进入 uncertain 之后都会拒绝写操作」。
2. **没有故障注入层。** 物理执行的核心风险集中在故障路径上：超时、断连、重复请求、部分执行、取消。没有 fake 实现，这些故障就无法稳定复现。
3. **没有 parity 机制。** 迁移期间新旧路径并存，但无法自动判断两边行为是否一致。
4. **规则只存在于文字中。** AGENTS.md 写了规则，但没有机器检查。

## 3. 优秀参考、原则与结构

| URA 做法 | 借鉴 |
|---|---|
| 明确区分证据级别：CPU 检查不能证明真机成功 | 写进 a_global 5.2 |
| `--validate-config`、`doctor` 不依赖原生运行时 | 契约测试和布局检查都放在 CPU 上运行 |
| 对比工具 schema 和 prompt，变化以 diff 形式呈现 | 快照测试 |
| AGENTS.md 列出 review 禁止项 | 把禁止项变成可执行的检查 |

**原则**：

- 测试一个契约，而不是测试实现细节；
- 先补测试，再改契约；
- 不为了让测试通过而削弱断言；
- 离线证据和真机证据分开记录。

## 4. 目标设计

### 4.1 测试布局

沿用现有 CI，不新增顶层目录（a_global 5.2）：

```
tests/
  unit_tests/
    contracts/          # 跨模块契约：env / receipts / tools / result / prompt / artifacts / code_policy
    fault_injection/    # FakeEnvServer、FakeRpcTransport
    ...                 # 现有模块级测试
  parity/               # scripted planner 与 ParityRecord
  e2e_tests/            # 现有 GPU / 仿真测试
```

工具评估不放在 `tests/`：它和工具包一起放在 `toolkits/<name>/evaluation/`，用固定语料测量质量；`tests/unit_tests/toolkits/<name>/` 只放快速的契约检查。

### 4.2 契约映射

| 主题 | 契约测试 | 故障注入 | parity |
|---|---|---|---|
| a_2 | 拼装顺序与来源；记忆协议只有一份；prompt 中没有参数说明 | 变量缺失 | 新旧 prompt 的关键约束 |
| a_3 | 结果四层；能力到 schema 的矩阵；内置工具写记忆目录被拒绝 | 参数校验失败、未知工具、工具异常 | 旧 `data` 与四层结果的字段对照 |
| a_4 | `robo.<tool>()` 与 tool call 返回同一个结果 | cell 超时、cell 内出现 uncertain | 同一脚本在两种调用模式下的 step 序列 |
| a_5 | adapter 实现 a_5 4.2 的方法集；不支持的控制模式不声明、调用时抛 `RequestRejected`；`episode_over` 不等于成功 | `RequestRejected` 只在第一次原生调用前抛出；其他原生异常映射为 `unknown` | 迁移前后的工具名与 feedback |
| a_6 | `EnvReceipt.status` 五种状态及到 `ToolResult` 的映射；`unknown` 与 `not_started` 的区分；`partial` 不锁存 | 执行后丢失回执、重复 id、`sequence` 倒退、服务端崩溃、客户端超时、自动对账后解锁、取消产生 `partial`、reset 后 `sequence` 归零 | 新旧路径的动作执行次数 |
| a_7 | `RunFinalizationContext` 互斥约束；finish 策略表；退出码；evaluate 模式结果中无真值字段，操作员判定也不进入模型上下文；`truth_source` 与实际通道一致 | uncertain 与 timeout 应判为 retryable | 新旧口径的成功率对照 |
| a_8 | manifest schema；原子写；事件关联字段 | 写入失败、在同一目录重跑、并发写事件 | Dashboard 事件序列 |

测试命名采用「给定输入 → 期望契约」的形式。失败信息里包含 `run_id`、`tool_call_id`、`request_id`，便于定位。

### 4.3 parity harness

`tests/parity/harness.py`：

- **输入**：固定 seed、固定 task，以及回放固定 tool call 序列的 scripted planner；
- **输出**：`ParityRecord`，包含 tool calls、四层结果的关键字段、step（`state_version` 与产物）、`RunFinalizationContext`，以及 prompt 关键约束是否存在；
- **对比**：允许白名单内的差异，例如新增字段、已知的文案变化。白名单要写进 PR 描述，并由 reviewer 确认；
- **运行条件**：不调用 LLM，不依赖 GPU。真机切片只对照回执、锁存和门控等可以观察到的行为。

### 4.4 CI 检查

新增一个脚本（`check_layout`）和一个测试（schema 快照），并接入 a_1 的两条安装检查。级别按 a_1 4.6：K1、K4、K5 先以 warning 运行并在 S3 转 error；K2、K3 随 S3 直接以 error 上线；K6 随 S2 以 error 上线；K7 保持 warning：

| 检查 | 形式 | 规则 |
|---|---|---|
| `check_layout` | 新增 `scripts/check_layout.py`，挂进 `pre-commit` | 规则清单见 a_1 4.6（K1 目录白名单、K2 组件必需文件、K3 禁用旧名、K4 越界 import、K5 核心不出现机器人名、K6 入口惰性、K7 切片文件行数）；另加两条：`robots/*` 不得定义工具族已有的工具名（R1）；prompt 片段里工具参数名后不得紧跟默认值或单位（a_2） |
| 组件清单与配方 | `rpent-env check --all`（a_1），挂进 `pre-commit` 或独立 CI job | schema 合法；冲突对称；配方闭包无越界放置；Python/平台范围可满足；不下载依赖 |
| schema 快照 | `unit_tests/contracts/test_tool_schemas.py` | `tools.json` 与快照一致；根节点为 `additionalProperties: false` |
| 文档 | `Docs` workflow 的两个 Sphinx 构建（`-W --keep-going`）与 Read the Docs（`fail_on_warning: true`），加 `scripts/check_docs.py` | RST 指令、`:doc:`/`:ref:`、include 与 directive 路径由 Sphinx 决定；Markdown 链接、同文件锚点、Validation Status 表与证据、文档命令中的仓库路径与设计状态行由 `check_docs` 决定；两者不重复解析同一类引用 |
| 安装 | fresh venv + `rpent-env install` + `rpent-env doctor` | 每个受支持配方在 nightly 安装一次；release 前全部通过 |

prompt 快照、产物 schema 和 flag 矩阵都由契约测试覆盖，不再单独设 CI job。

### 4.5 工具评估

契约测试回答「工具是否破坏约定」，工具评估回答「这次改动让工具变好还是变坏」。两者不能互相替代。

| 层 | 位置 | 输入 | 运行时机 | 输出 |
|---|---|---|---|---|
| 快速检查 | `tests/unit_tests/toolkits/<name>/` | 合成观测、fake model | 每个 PR | pass/fail |
| 冻结重放 | `toolkits/<name>/evaluation/` | 感知：冻结 RGB-D、点选、mask；动作：脚本化场景 | 工具改动、nightly | coverage + 误差分布 |
| 全量实验 | 同上，输出到源码树外的临时目录 | 真实模型服务 | 手动触发 | 单一基线报告 |

规则：

- **参考独立**：参考来自模拟器网格和同帧 FK，不读工具输出、mask 或点选；
- **语料版本化**：改动固定清单要升版本，前后对比只在同一版本内做；
- **不只报均值**：coverage、`warning` 比例、尾部误差一起报；
- **badcase 回填**：每个真实失败要么进下一版语料，要么变成回归测试；
- **不设自动通过阈值**：评估产出证据，合入由 reviewer 判断，证据格式遵循 a_0 4.3。

工具评估不替代故障注入：评估测的是输出质量，故障注入测的是超时、重复请求和不确定态。

## 5. 目标与非目标

**目标**

- 每个主题的验收条件都对应到具体测试；
- 故障注入覆盖 at-most-once、不确定态、取消和重复请求；
- 每次迁移都有 parity 记录；
- 感知工具改动都附同一语料的前后对比，badcase 有回归归属；
- 每个受支持配方都有 fresh-install 记录，安装漂移能被 doctor 发现；
- 现有测试一个都不削弱。

**非目标**

- 不追求覆盖率数字，也不引入新的测试框架；
- 不在每个 PR 上跑全量 benchmark，只跑固定 seed 的小集合，全量放在 nightly；
- 不用工具评估替代契约测试或故障注入，也不为每个工具强行建立 benchmark；
- 不自动化真机动作，也不为 RLinf 做跨仓库持续集成（通过 pin revision 解决）。

## 6. 如何实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1 基础设施** | 创建 `contracts/`、`fault_injection/`、`parity/` 目录，以及共享 fixture | 与 a_5 P1 同一个 PR 合入 |
| **P2 随主题补齐** | 每个主题的 P 阶段都带上对应的契约测试 | 映射表逐行有测试文件链接 |
| **P3 故障注入** | 回执、重复请求、超时、取消、代码模式超时 | 至少 10 个场景全部通过；a_6 只有在这些场景通过后才算完成 |
| **P4 parity** | harness 搭建，并完成 RoboTwin 试点对照 | 试点有完整的 parity 报告 |
| **P5 CI** | `check_layout` 与 schema 快照 | 至少有一次故意违规被拦截 |
| **P6 工具评估** | 与 a_3 P4 同步建 `toolkits/geometry/evaluation/`，接入冻结重放与 badcase | 80 cases 能在 CPU 上重放；报告有 coverage 与分组误差 |
| **P7 安装检查** | 与 a_1 P1–P2 同步接入 `rpent-env check --all`、fresh-install nightly 和 doctor | 现有 15 对冲突全部能被清单检查复现；3 个试点配方可安装；release 前 doctor 全部通过 |

## 7. 验收指标

| 指标 | 基线 | 目标 |
|---|---|---|
| 验收条件映射到测试的比例 | 0 | 100% |
| 故障注入场景 | 少量私有测试 | ≥10 个共享场景 |
| 有 parity 记录的已迁移切片 | 0 | 100% |
| 可机器检查的规则 | 0 | R1（工具名）、R2、R8、K4（import 边界）、R12 和 schema |
| 感知工具改动附评估报告的比例 | 0 | 100% |
| 已修 badcase 的回归归属 | 无 | 每个都有 |
| 有 fresh-install 记录的受支持配方 | 0 | 100% |
| 安装漂移能被 doctor 发现 | 否 | 是 |
| 被削弱的现有测试 | — | 0 |

## 8. 风险

| 风险 | 对策 |
|---|---|
| 测试数量膨胀 | 按契约写测试，一个契约一个文件，复用 fixture |
| parity 误报 | 白名单必须由 reviewer 确认，并写进 PR 描述 |
| CPU 测试带来虚假信心 | 离线证据和真机证据分开记录 |
| 护栏过严，阻碍开发 | 先以 warning 运行一个 release；豁免必须写明到期时间 |
