# a_1 隔离组件依赖与安装
> 状态：草案｜基线 `01e9cb3`｜最后更新 2026-11-13

> 依赖跟着组件走，环境按具名配方组装，安装结果有指纹；冲突在安装前暴露，缺少组件时直接告诉用户装什么。
>
> 前置阅读：[a_global](a_global.md) 第 3、4 节与 R7/R8/R10；[a_5](a_5_精简机器人接入.md) 的切片边界；[a_3](a_3_抽出共享工具族.md) 的工具包边界。

## 1. 问题背景

RPent 用一个 `pyproject.toml` 装下所有平台：`dependencies` 放核心，14 个 extras 放 robot、sim 和 model。extras 能表达「多装一组」，不能表达「这两组不能一起装」，也不能表达「这个组件应该在另一个环境里」。当组件数量增长，维护成本就从代码转移到了安装。

当前 `pyproject.toml` 309 行，其中 optional dependencies 约 115 行：14 个 extra，7 个通过 `rpent[...]` 继承其他 extra，15 对 `[tool.uv] conflicts`。这些数字还在增长，而且只覆盖了已知冲突。

**真实的依赖冲突不是个别现象：**

| 冲突 | 具体表现 |
|---|---|
| 同名包不同来源 | `rlinf` 在常规 extra 里是 `RLinf/RLinf@release/v0.4`，在 `robodojo-sim` 里是 `littleZ05/RLinf@rpent/robodojo`；resolver 无法同时满足 |
| 同一个包多个 pin | torch：OpenPI 2.7.1、RoboDojo override 2.7.0、CUROBO 构建 2.8.0；transformers：OpenPI 4.53.2 与 Molmo `>=4.57` |
| 仿真器互斥 | LIBERO 要求 `mujoco==3.3.0`，YAM 要求 `mujoco>=3.2,<4`；Franka 要求 `gymnasium==0.29.1` 和 `numpy<2` |
| 需要用 override 才能装 | `requirements/robodojo-override.txt` 为 RoboDojo 覆盖 8 个 pin（starlette、typing-extensions、uvicorn、torch 等），必须手工附加到安装命令 |
| 冲突只写在注释里 | `molmo` extra 的注释说明它和 OpenPI 的 transformers pin 冲突，但 `[tool.uv] conflicts` 只列了 `robotwin × molmo`，没有列 `libero × molmo` |

**安装知识分散在仓库各处：**

- 英文文档 8 个文件、中文文档 8 个文件各有 17 处 `uv pip install -e ".[...]"`，合计 34 处；extra 引用共 64 处；
- `tests/e2e_tests/run_gpu_suite.sh` 已经按 target 创建独立 venv、安装对应 extra 并运行 `uv pip check`，但 target → extra → Python 版本的映射写在脚本里；
- `docs/source-en/rst_source/development/add_action_model.rst` 明确说模型依赖放在单独环境，`molmo_server.py` 的 docstring 要求用另一个解释器并通过 `PYTHONPATH` 启动；
- 这些做法本身是对的，但它们不是仓库级契约，新增一个平台要同时改 pyproject、workflow、脚本和文档。

**工具包没有安装位置。** `pyproject.toml` 的 `[tool.setuptools.packages.find]` 把 `toolkits*` 排除在打包之外（第 269 行）。a_3 和 #341 让 `toolkits/geometry/` 拥有实现和评估，但它不随包安装，依赖也没有声明位置。

**安装结果不可追溯。** 没有 lock 文件，没有安装清单，`run.json` 也不记录环境；事后无法回答「这次运行用的是哪个 profile、哪些组件、什么 Python、哪套依赖」。

| 症状 | 证据 |
|---|---|
| 一个 extra 是一组隐式依赖 | 7 个 extra 继承其他 extra |
| 冲突靠手写矩阵 | 15 对 `conflicts`，仍会漏 |
| 某些组合必须手工 override | RoboDojo 的 8 个 pin |
| 工具包不参与安装 | `toolkits*` 被 exclude |
| 安装说明分散在 16 个页面 | 中英文各 8 个页面，外加 CI 脚本 |
| 装完不可追溯 | 无 lock、无 install manifest、`run.json` 无环境字段 |

## 2. 根因

1. **依赖的归属错了。** 依赖属于组件（一个机器人、一个工具、一个模型能力），不属于项目。现在所有组件的依赖都堆在根 `pyproject.toml`，再用 extra 当命名空间；extra 只是标签，不能表达冲突、不能单独锁、不能表达运行时位置。
2. **extra 不是组件。** 它没有导入探针，没有 Python / 平台范围，没有所有者，也不能声明「我需要另一个组件」。`libero = ["rpent[rlinf,sam3]"]` 这种继承把组合关系藏进了字符串。
3. **环境没有一等表达。** 哪些组件能同时装，只存在于 `[tool.uv] conflicts`、CI 脚本和文档文字里；用户只能靠记忆。
4. **安装不是产物。** 安装完没有清单，没有锁，没有 doctor；环境漂移只能靠运行时异常发现。
5. **组件边界和安装边界不一致。** `robots/<name>/` 是完整实例却没有依赖声明；`toolkits/<name>/` 是独立工具却被排除在安装之外。
6. **缺依赖的失败不指向安装动作。** 可选依赖在 import 时才炸，用户看到的是 `ModuleNotFoundError: torch`，而不是「组件 sam3 未安装，运行 rpent-env install sam3」。

## 3. 优秀参考、原则与结构

| 参考 | 说明 | 借鉴 |
|---|---|---|
| uv extras / conflicts / workspace | extras 是加法；`conflicts` 显式表达互斥；workspace 支持多包 | 互斥必须显式声明，并由安装前检查消费 |
| PEP 735 dependency groups | 开发、测试依赖与运行时依赖分开 | `test` 不再是 extra，dev 用 dependency group |
| RLinf `requirements/embodied/{envs,models}` | 按环境和模型组织依赖文件，安装脚本组合 | 按组件组织依赖；**不照搬**它 4700 行的 `install.sh` |
| RPent GPU suite | 每个 target 一个干净 venv，安装后跑 `uv pip check` | 已有正确做法，把它变成配方和 CI 契约 |
| Molmo 独立解释器 + RPC | 冲突的模型栈放另一个环境，用 endpoint 连接 | 「外部环境」是正式放置方式，不是文档脚注 |
| `requirements/robodojo-override.txt` | 某些组合需要显式 override | override 跟着组件走，并记录原因 |

**原则：**

- 依赖跟着组件走，项目只保留核心依赖；
- 一个依赖的版本约束只有一个所有者，其他组件只声明包名；
- 冲突显式声明，安装前检查，运行时不需要猜；
- 环境是具名配方，不是任意组合；配方可以包含外部环境；
- 核心在最小环境里必须可安装、可导入、可发现机器人、可显示 `--help`；
- 安装结果可复现、可诊断、可追溯；
- 不引入第二套包管理器，继续用 `uv`。

## 4. 目标设计

### 4.1 组件、配方与指纹

三个概念：

```
组件清单 component.toml ──┐
                          ├──> 环境配方 envs/<profile>.toml
组件代码（robots/、       │         │
toolkits/、能力目录）─────┘         ▼
                              依赖集合 + lock
                                    │
                                    ▼
                          venv + rpent-install.json ──> run.json 记录指纹
```

- **组件**是安装边界：一个目录、一份 `component.toml`、一个导入探针、一组直接依赖；
- **配方**是运行边界：把若干组件按放置方式组合成一个可安装环境，只有具名配方受支持；
- **安装指纹**是证据边界：安装成功后写在 venv 里的 `rpent-install.json`，记录配方、清单 hash、锁和平台，`run.json` 引用它。

**这里不按 extra 把仓库拆成十几个发行包。** 冲突发生在「同一个环境能否同时解析」，不在发行元数据；拆包后仍然要共享 lock 或逐包解析，还会引入 namespace package、独立版本号和发布成本。组件清单拿到依赖所有权，环境配方拿到安装隔离。将来某个组件确实需要独立发版时，`component.toml` 的字段可以机械提升为 `pyproject.toml`，不需要重写依赖。

### 4.2 组件清单：`component.toml`

组件目录自带清单：

```
robots/libero/
  component.toml
  __init__.py  robot_spec.py  config.py  ...
toolkits/geometry/
  component.toml
  tool.py  core.py  observation.py
  evaluation/
rpent/robots/components/sam3/
  component.toml
  client.py  server.py
```

`component.toml` 的字段：

```toml
schema = 1
name = "libero"
kind = "robot"                    # robot | toolkit | capability
probe = "robots.libero"           # 导入探针，doctor 用
python = ">=3.10,<3.13"
platforms = ["linux-x86_64"]
requires = ["rlinf", "openpi", "sam3"]
env_conflicts = ["franka", "robotwin", "robodojo"]
placement = ["in-env"]            # in-env | external-env | remote
docs = "docs/source-en/rst_source/simulators/libero.rst"

dependencies = [
  "rpent-libero @ git+https://github.com/RLinf/LIBERO.git@rpent",
  "mujoco==3.3.0",
]

[optional]
pro = ["rpent-liberopro @ git+https://github.com/RLinf/LIBERO-PRO.git@rpent"]
plus = ["rlinf-liberoplus", "h5py"]
```

| 字段 | 作用 |
|---|---|
| `name` | 组件名，配方内唯一 |
| `kind` | robot / toolkit / capability，决定审查规则 |
| `probe` | 导入路径；`doctor` 用它验证组件真的可用 |
| `python` / `platforms` | 明确支持范围；不满足时安装前报错，而不是装出一个空环境 |
| `requires` | 依赖的其他组件；闭包由安装器计算，不复制依赖 |
| `dependencies` | 本组件直接需要的包；只写自己需要的 |
| `optional` | 组件级可选依赖组，例如 `pro`、`plus`、`eval` |
| `env_conflicts` | 不能装进同一环境的组件；检查器按对称闭包处理 |
| `placement` | 允许的放置方式，配方只能从允许集合里选 |
| `overrides` | 组件自己的 constraints / override 文件（可选） |
| `docs` | 组件文档路径（可选） |

`env_conflicts` 只写一次即可，检查器按对称闭包处理；两边都写但不一致时报错。版本冲突可以显式写进 `env_conflicts`，也可以由同一环境的重复 pin 检查发现；前者优先，因为 resolver 的报错不可读。`rpent-env check` 先比较直接约束，`--resolve` 再用 `uv pip compile` 确认兼容区间。

边界规则：

- **只声明直接依赖。** `libero` 需要 OpenPI，就写 `requires = ["openpi"]`，不要把 OpenPI 的包再抄一遍；
- **版本约束只有一个所有者。** torch 的 pin 属于 `openpi` 或对应配方，`sam3` 只声明 `torch`；同一个环境里出现两个不同的 pin，`rpent-env check` 报错；
- **可选依赖只在用到处导入。** 并由统一的 guard 报错（4.6），不再抛裸 `ImportError`；
- **组件之间不互相 import 代码。** `toolkits/*` 不 import `robots/*`，`robots/*` 不 import 另一个 `robots/*`，`capability` 不 import 机器人；由 `check_layout` 检查；
- **组件没有独立版本号。** 组件版本就是「源码 commit + 清单 hash」；仓库整体发版，避免多个版本号互相漂移；
- **共享能力按 R7 抽取。** 只有两个以上消费者才成为独立 capability；只有一个消费者的依赖留在组件自己的 `dependencies` 里。

### 4.3 环境配方：`envs/<profile>.toml`

```toml
schema = 1
name = "libero-pro"
python = "3.11"
platform = "linux-x86_64"
lock = "envs/locks/libero-pro.lock"

[components.libero]
placement = "in-env"
variant = "pro"

[components.sam3]
placement = "in-env"

[components.molmo]
placement = "external-env"
env = "molmo"
```

规则：

- **受支持目标只走具名配方。** 不在命令行上接受任意组件组合；需要新组合就加一个配方并评审。单组件安装只用于开发诊断，不算受支持目标；
- **Python 和平台写死到 minor。** LIBERO-PRO 用 3.11、RoboCasa 用 3.10、Franka 的 wheel 带 cp310–cp312 标记；配方不再依赖 resolver 去猜；
- **`in-env` 组件检查 `env_conflicts`。** 两个互斥组件只有在其中一个放到 `external-env` 时才允许出现在同一配方；
- **外部环境有独立配方。** `molmo` 自己是一个配方，`libero-pro` 只引用它的 endpoint；
- **配方是受支持目标的唯一入口。** 文档、CI、用户命令都指向配方，不直接指向 extra。

现有 extra 的对应关系（迁移目标）：

| 现有 extra | 目标 |
|---|---|
| `test` | `dev` 配方或 dependency group |
| `rlinf` / `sam3` / `openpi` / `molmo` | capability 组件；`molmo` 只有外部配方 |
| `libero` / `libero-pro` / `libero-plus` | `libero` 组件加三个配方（`pro`、`plus` 是组件的 optional 组） |
| `franka` / `yam` / `robocasa` / `robotwin` / `robodojo` | 同名 robot 组件与配方 |
| `robodojo-sim` | `rlinf-robodojo` capability（与 `rlinf` 互斥）加 `robodojo` 自己的仿真依赖 |
| `flywheel` | LIBERO 配方的可选组，或独立的 `libero-flywheel` 配方 |

### 4.4 安装器：`rpent-env`

新增一个 console script `rpent-env` 和 `rpent/cli/env.py`，与 `rpent-check-llm`、`rpent-memory` 同级：

| 命令 | 作用 |
|---|---|
| `rpent-env list` | 列出组件、配方和放置方式 |
| `rpent-env check <profile>` | 只做清单、闭包、冲突、Python/平台检查，不创建环境；`--all` 检查全部配方 |
| `rpent-env install <profile\|component>` | 创建或复用 venv，安装依赖，跑探针，写安装指纹；单个组件用于开发诊断 |
| `rpent-env lock <profile>` | 生成或更新依赖锁；`--check` 在 CI 里校验锁是否过期，`--all` 覆盖全部配方 |
| `rpent-env doctor [--profile]` | 校验当前环境：Python、平台、探针、`uv pip check`、外部 endpoint |
| `rpent-env inspect` | 打印当前 venv 的安装指纹和漂移 |

安装流程：

1. 读取配方，计算 `requires` 闭包；
2. 按 `placement` 分组：`in-env` 进主环境，`external-env` 进各自环境，`remote` 不安装；
3. 检查闭包内的 `env_conflicts`、重复 pin、Python/平台；
4. 生成确定性的依赖文件 `.rpent/envs/<profile>.txt`，顺序固定，便于 diff；
5. `uv venv`（仅当不存在），然后 `uv pip install -r ... -e .`（有锁时用锁）；核心依赖也写进依赖文件，`-e .` 只负责安装代码；
6. 跑每个组件的导入探针和 `uv pip check`，全部通过后才写 `<venv>/rpent-install.json`。

安装指纹示例：

```json
{
  "schema": 1,
  "profile": "libero-pro",
  "python": "3.11.9",
  "platform": "linux-x86_64",
  "source_commit": "01e9cb3",
  "source_dirty": false,
  "components": {
    "libero": {"manifest_sha256": "...", "placement": "in-env", "variant": "pro"},
    "sam3": {"manifest_sha256": "...", "placement": "in-env"},
    "molmo": {"manifest_sha256": "...", "placement": "external-env", "env": "molmo"}
  },
  "requirements_sha256": "...",
  "freeze_sha256": "...",
  "lock": "envs/locks/libero-pro.lock",
  "installed_at": "2026-11-13T10:00:00Z"
}
```

- `requirements_sha256` 是输入（配方 + 组件清单）的 hash，`freeze_sha256` 是安装后 `uv pip freeze` 的 hash；
- `rpent-env doctor` 重新计算两者，漂移就报「环境已过期，重新运行 install」；
- `run.json` 记录 `profile` 和安装指纹的 sha256（a_8）。

失败信息必须指向动作，而不是栈：

```
$ rpent-env check libero-molmo
组件冲突：配方把 molmo 放在 in-env，与 openpi 不能同环境安装
  openpi 需要 transformers==4.53.2
  molmo 需要 transformers>=4.57
可选：
  1) 把配方里的 molmo 改为 external-env（推荐）
  2) 只安装 libero：rpent-env install libero
```

```
ImportError: 组件 sam3 未安装（缺少 torch, sam3）
  当前环境：.venv（profile: minimal）
  安装：rpent-env install sam3 --venv .venv
```

**兼容期：** 根 `pyproject.toml` 的 extras 由 `scripts/gen_extras.py` 从组件清单和配方生成，保证 `pip install -e ".[libero]"` 在一个 release 内仍然可用；`molmo` 不再作为可继承 extra，改为外部配方。一个 release 后删除生成的 extras，文档只保留 `rpent-env`。

### 4.5 运行时放置

放置方式只描述「装在哪里」，不描述「谁拉起进程」；进程所有权仍由 a_5 的 `RobotSpec.init_runtime` 和 a_6 的回执管理。

| 组件 | 默认放置 | 理由 |
|---|---|---|
| 环境 adapter、prompt、toolkit | `in-env` | 与 RPent 同进程族，只依赖核心契约 |
| SAM3 | `in-env` 或 `external-env` | torch/CUDA 重；可共享，也可隔离 |
| OpenPI / Pi0.5 | `in-env` 或 `external-env` | 固定 torch / transformers，适合独立环境 |
| Molmo | `external-env` 或 `remote` | transformers `>=4.57` 与 OpenPI 的 4.53.2 冲突 |
| RLDX / LingBot / 厂商运行时 | `external-env` 或 `remote` | 厂商环境不可控 |
| Flywheel | `in-env`（可选） | 只在导出时用 |

- `external-env` 组件有自己的配方和 venv；RPent 通过 endpoint 连接，沿用现有的 `--molmo-endpoint`、`--am-endpoint`；
- RPent 不在运行时安装依赖、不下载权重；缺环境时报 doctor 的错误；
- 进程是 owned 还是 borrowed 由 a_5 决定：owned 进程由 RPent 启动和停止，borrowed endpoint 保持运行。

### 4.6 功能隔离的机器检查

安装隔离之外，组件之间还要有代码边界；否则「隔离」只是目录上的：

- `check_layout` 增加 import 规则：`toolkits/*` 不得 import `robots/*`；`robots/<a>` 不得 import `robots/<b>`；capability 不得 import 机器人；核心不得 import `robots/*` 或 `toolkits/*`；
- 最小环境测试：只安装核心和 `dev`，验证 `import rpent`、`rpent --help`、`enumerate_robots()` 都可用；
- 可选依赖统一 guard：

```python
from rpent.components import require

torch = require("sam3", "torch")
```

`require` 根据当前安装指纹找到组件名和安装命令，抛出可读错误；禁止组件自己写 `try: import torch except ImportError: torch = None`。

### 4.7 文档与 CI 收敛

- 新增一页 `installation`，按配方写安装；各机器人页面只保留平台准备（GPU、资产、checkpoint），安装命令统一为 `rpent-env install <profile>`；
- `docs-check` 增加规则：机器人页面里的安装命令只能是这一种形式；兼容期例外只允许出现在 installation 页；
- PR 检查跑 `rpent-env check --all`（只读清单，不下载依赖）和最小环境单测；
- nightly 对每个受支持配方做一次 fresh venv 安装 + doctor；GPU e2e 继续按 target 触发，但脚本改为读配方，不再维护 target → extra → Python 的映射；
- release 检查所有锁是否过期；`rpent-env lock --check` 失败则阻止发布。

## 5. 目标与非目标

**目标**

- 根 `pyproject.toml` 只保留核心依赖，不再认识 robot / sim / model；
- 每个 robot、toolkit、共享能力都有 `component.toml`，声明直接依赖、探针、Python/平台和冲突；
- 每个受支持目标都有具名配方、依赖锁和 fresh-install 记录；
- 冲突显式、对称、安装前可检查；已知组件的冲突不再依赖注释；
- 缺少组件时的错误信息直接给出安装命令；
- 工具包像组件一样参与安装，评估依赖不与运行时依赖混在一起；
- 每次运行都能从 `run.json` 追到安装指纹。

**非目标**

- 不把仓库拆成多个 PyPI 发行包，也不引入组件级版本号；
- 不保证从 wheel 安装任意组件；组件安装以源码检出为前提，与当前文档一致；
- 不引入 conda、pixi 或第二套 resolver；Docker 可以作为部署产物，但不是安装事实源；
- 不支持命令行任意组合多个组件；受支持目标只走具名配方；
- 不在运行时 `pip install`、下载权重或修改环境；
- 不为第三方组件设计插件发现机制；等出现第二个仓库再引入 entry points；
- 不要求每个配方都带 hash 锁：有 VCS 依赖的配方记录 commit 和冻结版本即可；
- 不用安装检查替代运行时 e2e；安装通过只证明依赖可解析、探针可用。

## 6. 如何实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1 清单与检查** | 为 3 个试点（LIBERO、RoboTwin、Franka）、`sam3`、`openpi`、`geometry` 写 `component.toml`；写 `envs/` 试点配方；实现 `rpent-env check` | 现有 15 对冲突全部由清单表达；至少补上 `libero × molmo` 这类隐式冲突；3 个试点配方可解析；core 不新增依赖 |
| **P2 安装与指纹** | `install`、`doctor`、`rpent-install.json`；最小配方和一个 GPU 配方进 CI；`run.json` 记录指纹 | 干净机器上一条命令装出可用环境；doctor 能发现手工 `pip install` 造成的漂移 |
| **P3 能力与工具包** | 把 `sam3`、`openpi` 抽成 capability；`toolkits/geometry` 带 `component.toml` 和 `eval` 可选组；RoboDojo override 移进组件目录；建立 `rlinf-robodojo` 与 `rlinf` 的互斥 | 组件目录自包含；`geometry-eval` 配方可单独安装；RoboDojo 不再需要手工传 override |
| **P4 外部环境** | `molmo` 外部配方与 endpoint；OpenPI 可选外部放置；doctor 检查 endpoint | `libero-pro` 与 Molmo 同配方运行；不把两个 transformers 版本装进同一 venv |
| **P5 锁、文档与退役** | 生成锁并接入 nightly/release；安装文档收敛；一个 release 后删除生成的 extras | 所有受支持配方有锁；文档只剩一种安装命令；`pyproject.toml` 不再有机器人依赖 |

P1 和 P2 可以并行；P3 依赖 P2 的组件模型；P4 依赖 P3 的 placement；P5 最后做，避免在迁移期同时改文档和安装器。

## 8. 风险

| 风险 | 对策 |
|---|---|
| 清单与实际 import 漂移 | 组件探针 + 每个配方的 fresh-install 测试；新增依赖必须同时改清单 |
| 配方数量膨胀 | 只接受具名配方；新增配方需要 CI 记录和评审，不提供任意组合参数 |
| 锁文件频繁变化 | 只在组件改动或 release 时重锁；锁 diff 进 PR 评审，不 nightly 自动提交 |
| 外部环境增加使用成本 | `rpent-env install` 一次装好；doctor 检查 endpoint；文档给一个完整示例 |
| override 掩盖真实不兼容 | override 文件必须写原因和影响范围；安装通过后仍要跑对应 target 的 e2e |
| 迁移期两套入口并存 | extras 只作为生成别名保留一个 release，删除日期写进 PR |
| 组件拆分过细 | 按 R7 只抽两个以上消费者的能力；单消费者的依赖留在组件内 |
| 核心仍被间接拖重 | CI 的最小环境测试和 `pip check`；核心依赖新增需要说明两个使用方 |
| 安装通过被误当成真机可用 | 安装检查只进 CPU 证据档；真机证据仍按 a_0 的三级证据分开记录 |
