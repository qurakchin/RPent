# a_2 拼装提示词
> 状态：草案｜基线 `01e9cb3`｜最后更新 2026-11-13

> prompt 不再由每个机器人手写一整棵树，而是由「片段库 + 工具族贡献 + 领域片段」按固定层序拼装，并产出可追溯的 prompt 文件。
>
> 前置阅读：[a_global](a_global.md) R1/R9；[a_3](a_3_抽出共享工具族.md) 的 `SceneTools` / `MotionTools` / `MemoryTools` / `CommonTools` 的 `prompt_sections`。

## 1. 问题背景

- `PromptBundle` 只有 `system` 和 `user` 两个工厂（`rpent/robots/prompt_bundle.py:32-47`），由 `format_prompt` 把 Python 树渲染成 Markdown。共享内容只有 `rpent/prompt/common.py` 的 39 行。
- 切片 prompt 合计约 3.0k 行：

  | 切片 | 行数 |
  |---|---|
  | LIBERO | 1269 |
  | RoboCasa | 434 |
  | RoboTwin | 385 |
  | dual_franka | 353 |
  | YAM | 231 |
  | RoboDojo | 186 |
  | Franka | 120 |

- PR #340 又为代码模式新增了 7 份切片 prompt，共 794 行（见 a_4）。
- 记忆协议在每个切片的 explore prompt 里各写一遍；工具的用法和参数说明写在 prompt 里，与 schema 重复。
- 没有 `effective_prompt.md`。transcript 只保存 `messages`、`task_desc`、`stats`（`rpent/cli/main.py:716-728`），无法回答「这次运行给模型看了什么」。
- Claude Code 和 Codex 两条路径把 system prompt 拼进了第一条 user 消息（`claude_code.py:116`、`codex.py:146`），这种差异在产物中也看不出来。

## 2. 根因

1. **prompt 按机器人复制，而不是按能力拼装。** base 规则、运行模式、工具用法、记忆协议、领域知识全写在每个切片里，导致通用内容改一处、要改七处，不同切片之间也不一致。
2. **没有贡献接口。** 工具族无法为自己的工具提供用法说明，运行模式也没有共享片段。
3. **没有 prompt 产物。** 无法做快照测试，也无法定位行为变化是不是 prompt 引起的。

## 3. 优秀参考、原则与结构

URA 的 `assemble_prompt`（`context/prompt.py:82-134`）按固定顺序组装 prompt：base → runtime 片段 → 交互模式片段 → 模块提供的 prompt → observation 贡献 → storage 说明。组装完成后写出 `effective_prompt.md`，并在 `Prompt.sources` 中记录每段来源；`{{var}}` 缺少变量时直接报错。

**借鉴**：

- 固定的组装顺序；
- 记录来源；
- 产物落盘；
- 变量严格替换；
- 工具说明由工具模块自己提供。

**不照搬**：跨 planner 的 context policy 抽象。Claude Code 和 Codex 的上下文由 SDK 管理，三个 planner 中有两个控制不了，为剩下的一个消费者单独建抽象层不划算。

**原则**：

- 通用内容只写一份；
- 参数约束只出现在 schema 里；
- 切片只写领域知识；
- 能力不同，prompt 也跟着不同。

## 4. 目标设计

### 4.1 拼装顺序

```
base → mode → tool families(caps) → robot domain → memory 指针
```

| 层 | 内容 | 由谁提供 |
|---|---|---|
| base | 角色、总原则、输出与产物规则 | `rpent/prompt/fragments/base.md` |
| mode | `evaluate` / `explore` / `dashboard` / `real_robot` / `code` | 核心片段；代码模式的规则来自 PR #340 的 `rpent/prompt/code_policy.py` |
| tool families | 各族的用法，说明何时用、怎么组合、结果怎么读；随能力增减 | `SceneTools` / `MotionTools` / `MemoryTools` / `CommonTools` 的 `prompt_sections(caps)`（a_3） |
| robot domain | 布局、坐标约定、任务族、物体名、失败模式 | 切片 `prompts/domain.py`；tool call 与 code 两种调用模式共用 |
| memory | 只说明去哪里读、用哪个工具，不放记忆全文 | `fragments/memory_protocol.md` |

深度、标定、分割、VLA 等能力相关的说明由对应工具族提供，不另建能力片段，避免同一件事有两个来源。

### 4.2 片段库：`rpent/prompt/fragments/`

| 片段 | 内容 |
|---|---|
| `base.md` | 角色、总原则、输出习惯、产物保存 |
| `mode_evaluate.md` | 单次评测、不能 reset、`finish` 只表示提交、真值不可见 |
| `mode_explore.md` | 多次 attempt、reset、记忆写入流程 |
| `mode_dashboard.md` | 交互控制、暂停与恢复、operator 指令 |
| `mode_real_robot.md` | 真机安全、operator 确认、TTY 门控 |
| `memory_protocol.md` | 记忆读写与合并的**唯一**说明，配合 Memory 族的三个工具使用 |

每个片段只讲一件事，不出现机器人名。代码模式的规则保留在 `rpent/prompt/code_policy.py`（PR #340），作为 mode 层接入。

### 4.3 最小实现

```python
# 贡献单元沿用现有 PromptNode；渲染沿用 format_prompt / substitute_text
PromptNode = str | Mapping[str, Any] | Sequence[Any] | BulletList | Numbered

# rpent/prompt/assembly.py 新增：固定层序拼装
def assemble_prompt(
    parts: Sequence[tuple[str, str, str, PromptNode]],  # name / role / source / node
    *,
    variables: Mapping[str, object] | None = None,
) -> tuple[str, str, list[dict]]:
    """按固定层序渲染 system 与 user，并返回来源列表。"""
```

- 不引入优先级、条件表达式或模板 DSL；
- 现有 `PromptBundle`（`system` / `user` 工厂加 `render()`）用法不变，只是它的输出改为 domain 层的一项贡献，不再独占整个 prompt；
- 变量替换沿用现有的严格模式。

### 4.4 产物

每次运行写出以下产物：

| 产物 | 内容 |
|---|---|
| `effective_prompt.md` | 最终的 system 与 user 文本 |
| `prompt_sources.json` | 每段贡献的 `name / role / source / sha256`，以及该 planner 的拼接方式（例如 Claude、Codex 是 system-as-user） |
| `prompt_sha256` | 写入 `run.json`（a_8）；transcript 只引用这个值，不重复保存全文 |
| `--dump-prompt` | 只渲染 prompt 不运行，供调试 |

Claude 和 Codex 能分离 system 时，尽量通过 SDK 的 system 参数传入；做不到时，在 `prompt_sources.json` 里如实记录拼接方式。

## 5. 目标与非目标

**目标**

- 记忆协议、运行模式和输出规则全仓各写一份；
- 工具用法由工具族提供，prompt 中不再出现参数说明；
- 切片只保留领域知识，两种调用模式共用同一份；
- 每次运行都能回答「模型看到了什么」。

**非目标**

- 不引入模板 DSL，也不做自动 prompt 优化；
- 不删除 `PromptBundle`，只把它降级为领域贡献；
- 不做跨 planner 的上下文压缩抽象，API planner 现有的 `SlidingWindowCompaction` 保持原样。

## 6. 如何实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1 片段库与拼装** | 建 `fragments/` 与 `assemble_prompt`；把切片中重复的通用段落抽出来 | 记忆协议在全仓只出现一次；相同输入得到相同的 `prompt_sha256` |
| **P2 工具族贡献** | 接通 `prompt_sections(caps)`；删除 prompt 里的参数说明 | 增删工具族后 prompt 自动变化，切片不需要改动 |
| **P3 产物** | `effective_prompt.md`、`prompt_sources.json`、`--dump-prompt` | 每次运行都有这些产物 |
| **P4 迁移切片** | 顺序：RoboTwin → LIBERO → RoboCasa / RoboDojo → 真机 | 领域 prompt：LIBERO ≤300 行，其余切片 ≤150 行；新旧 prompt 的 diff 白名单进入 PR 描述 |

**迁移方法**：同时生成新旧两份 prompt 并做 diff，安全约束、记忆协议和 finish 语义逐条确认没有丢失，确认后切换。

## 7. 验收指标

| 指标 | 基线 | 目标 |
|---|---|---|
| 切片手写 prompt 合计（含 #340 的代码模式 prompt） | 约 3.0k + 0.8k 行 | ≤1.2k 行 |
| 单个切片的领域 prompt | 120–1269 行 | LIBERO ≤300 行，其余 ≤150 行 |
| 记忆协议份数 | 每个切片一份 | 1 份 |
| prompt 中的参数说明 | 多处 | 0（由 lint 检查，见 a_9） |
| `effective_prompt.md` 覆盖率 | 0 | 100% |

## 8. 风险

| 风险 | 对策 |
|---|---|
| 行为漂移（prompt 是模型行为的主要输入） | 快照测试 + 关键约束测试 + 固定 seed 冒烟 + diff 白名单；每次只迁一个切片 |
| 为了统一，把领域知识也塞进片段 | 片段只收通用内容，领域知识留在切片 |
| 工具贡献与 schema 不一致 | schema 和说明都由同一个 `SceneTools` / `MotionTools` / `MemoryTools` / `CommonTools` 生成 |
| 误以为三种 planner 看到的 prompt 完全相同 | 在 `prompt_sources.json` 中显式记录拼接方式 |
