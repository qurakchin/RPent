# a_6 建立执行回执语义
> 状态：草案｜基线 `01e9cb3`｜最后更新 2026-11-13

> 让每条物理写请求都可识别、可对账。不确定就停，永不重放。
>
> 前置阅读：[a_global](a_global.md) 2.1–2.2 节（名字、路径与身份）、R3/R4；[a_5](a_5_精简机器人接入.md) 的 `EnvReceipt` 与 `BaseEnvClient` / `BaseEnvFacade`。

## 1. 问题背景

RPent 把物理动作当作普通 RPC 调用：成功就拿到结果，失败就拿到一个错误。但物理动作不是幂等的，而一次 RPC「失败」可能对应三种完全不同的情况：

1. 请求没有到达服务端，动作**没有执行**；
2. 服务端**已经执行**，但响应丢失或客户端超时；
3. 服务端**正在执行**，客户端断开，结果未知。

现在这三种情况都表现为同一个 `RpcError`：

- `RpcClient.call` 失败时由 `check_response` 抛出 `RpcError`（`rpent/utils/rpc/rpc_client.py:87-97`）；
- `Toolkit.execute_tool` 把任何异常转成 `ToolResult(data={"error": ...})`（`rpent/tools/toolkit.py:265-269`）；
- 服务端 `RpcFacade._dispatch` 只做读写锁和异常封装，没有请求身份、序号，也没有结果缓存（`rpent/utils/rpc/rpc_facade.py:112-163`）。

于是上层只有两个选择：当作失败重试，可能**执行两次**；或者当作失败放弃，**丢掉已经完成的进度**。而且没有任何记录能说明第一次到底发生了什么。

相关处理分散在个别切片里，彼此没有共享：

| 切片 | 现有处理 | 位置 |
|---|---|---|
| RoboDojo | 原语出错时返回 `execution_uncertain` | `robots/robodojo/primitives.py:119-128` |
| dual_franka | e2e 夹具里锁存 uncertain | `tests/e2e_tests/dual_franka/dual_franka_vla.py:122-190` |
| YAM | 控制故障后标记 follower target 为 uncertain；operator receipt 带 `request_id` | `robots/yam/rlinf_env.py:524`、`robots/yam/operator_control.py:48` |
| RoboTwin、LIBERO、RoboCasa、Franka | 遇到同类故障**没有任何保护** | — |

## 2. 根因

1. **RPC 契约只描述调用结果，不描述执行状态。** gym 形状的 `step` 返回观测和 info，而不是回执。它是为同步训练循环设计的，训练时不需要考虑客户端重连。
2. **服务端没有账本。** 调用结束后什么都不保留，客户端拿着 `request_id` 回来查询也查不到。
3. **客户端把传输失败当成执行失败。** `RpcError` 里没有执行状态。
4. **锁存是切片私有的。** 别的切片没有锁存；锁存之后是否拒绝写操作，取决于各切片自己的实现；结果文件和退出码也表达不了「不可判定」。

## 3. 优秀参考、原则与结构

| 机制 | URA 的做法 | RPent 对应 |
|---|---|---|
| 请求身份 | `episode_id` / `request_id` / `sequence`，响应里的身份必须与请求一致 | 同样的字段，由 `BaseEnvClient` 分配（a_global 2.2） |
| 服务端去重 | 拒绝重复的 `request_id`，提示「读取已有结果，不要重放」 | `ReceiptLedger` |
| 结果分类 | `rejected / partial / completed / unknown`；未知失败一律报 `unknown` | `EnvReceipt.status` |
| 发出前拒绝 | adapter 抛 `RequestRejected`，明确没有执行 | 同名异常 |
| 客户端锁存 | 传输失败或 `unknown` 时锁存，之后拒绝所有写操作 | Episode 会话的 `uncertain` |
| 对账 | `reconcile()` 只读 `/requests/{id}`，从不重发 | `BaseEnvClient.reconcile()` |

**URA 做得不够的地方**：全包只有一处调用 `reconcile()`，在 finalize 阶段（`prepared_episode.py:209`）。丢一次 ACK，本 episode 的物理交互就整个终止。RPent 改为**运行中自动对账**，确认动作已完成或未执行时就解除锁存。

**原则**：

- 写请求必须有身份；
- 服务端负责记账；
- 客户端只对账、不重放；
- 只有「不知道执行到哪」才锁存；知道执行到哪的部分执行不锁存；
- 锁存放在共享层，不放在切片里；
- 读操作不进账本。

## 4. 目标设计

### 4.1 身份与回执

身份字段见 a_global 2.2：`episode_id`（每次 reset 新分配）、`request_id`、`sequence`（episode 内单调，reset 后归零）。回执类型是 a_5 的 `EnvReceipt`，它属于环境契约；`BaseEnvClient` 再把它映射成模型可见的 `ToolResult`（a_3 4.1）。

| `EnvReceipt.status` | 含义 | 是否锁存 | 上层处理 |
|---|---|---|---|
| `completed` | 动作完整执行 | 否 | 继续 |
| `rejected` | 发出动作前就被拒绝（`RequestRejected`、校验、生命周期） | 否 | 修正参数后可重试 |
| `not_started` | 服务端明确没有执行（例如排队时被取消） | 否 | 可以直接重试 |
| `partial` | 服务端明确执行了 `executed_steps` 步后停止（取消、步数上限、安全停止） | **否** | 记录步数和 `state_after`；不自动补偿，由模型基于新状态决定 |
| `unknown` | 可能执行了，但无法确认 | **是** | 只能对账 |

`partial` 不锁存，是因为服务端已经给出了确定的执行位置；这正是 Dashboard 打断一个 chunk（PR #199 的协作取消）的正常结果。锁存只留给真正不知道发生了什么的情况：`unknown` 和传输失败。

### 4.2 服务端账本

- `ReceiptLedger`（`rpent/env/ledger.py`）由 `BaseEnvFacade` 持有。`RpcFacade` 只新增一项能力：注册方法时声明 `write=True`，分发前后调用 facade 的钩子；
- 账本只在**内存**里按 `(episode_id, request_id)` 保存最近 N 条回执，默认 N=256，FIFO 淘汰；每个 episode 另外保留已见的 `sequence` 高水位，不随条目淘汰。重复的旧 id 即使已被淘汰，也会因为 `sequence` 低于高水位而返回 `rejected`，不会被当作新请求重放；
- 写方法分发前先查账本：
  - `request_id` 已存在：直接返回已有回执，不再执行；
  - `sequence` 小于该 episode 已见到的最大值：返回 `rejected`，不执行；
- 执行中：adapter 抛 `RequestRejected` → 记 `rejected`；其他异常 → 记 `unknown`，再返回错误；
- **账本不落盘。** 账本回答的是「同一个服务端进程里，这条请求执行到哪了」。服务端进程一旦重启，仿真或硬件状态已经和旧回执脱钩，落盘的旧回执也给不出可信的答案。所以重启后的未确认请求由客户端负责记录：它在 `events.jsonl` 里留下 `env_request(status=unknown)`（a_8），由 operator 或评测重跑处理。

### 4.3 客户端、锁存与自动对账

```
写调用 ──传输超时 / 断连 / unknown──> 锁存 uncertain
                                        │
              下一次写调用前：自动 reconcile(request_id)（只读）
                     │                           │
   completed / partial / not_started        unknown / 查不到
                     │                           │
                解除锁存，继续          保持锁存：写操作被拒绝，读操作放行
                                        真机：等待 operator 确认
```

- `BaseEnvClient.reset()` 分配新的 `episode_id`，并把 `sequence` 归零；锁存属于 episode，新的 episode 只能在锁存解除或 operator 确认之后开始；
- 传输层失败时抛出 `ExecutionUncertain(request_id, sequence)`，不再抛普通的 `RpcError`；
- 锁存状态放在 Episode 会话里（`uncertain`、`uncertain_requests`）。锁存期间：
  - 写工具在入口处直接返回 `execution_uncertain=True, no_execution=True`，不发出 RPC；
  - 读工具照常放行；
  - `finish` 放行，但这次运行被标记为 `retryable`（a_7）；
- 对账由框架自动完成，**不向模型暴露 reconcile 工具**；
- 切片不再自己实现超时、重试或锁存。

### 4.4 失败分流

| 失败类型 | 工具结果（a_3 四层） | 能否重试 |
|---|---|---|
| 参数校验失败、工具不存在 | `call_ok=False, no_execution=True` | 模型修正后可以重试 |
| 领域拒绝，例如 explore 下 `finish` 被拒 | `call_ok=True`，`error.code="refused"` | 由模型决定 |
| `rejected` / `not_started` | `no_execution=True` | 可以重试 |
| `partial` | `execution_status="partial"`，`data` 带 `executed_steps` | 由模型基于新状态决定，框架不自动重试 |
| `ExecutionUncertain` / `unknown` | `execution_uncertain=True` | **禁止**任何自动重试，包括 pydantic-ai 的 `ModelRetry` |

### 4.5 协议版本

- `EnvMeta.contract_version` 用于发现客户端和服务端版本不一致：不一致时直接报错，不做降级兼容；
- 新旧协议通过 `env_contract` 按切片切换（a_global 5.3），不另设开关。

## 5. 目标与非目标

**目标**

- 所有物理写路径都带身份，重复请求不会再次执行；
- 不确定即锁存，运行中能自动对账恢复；已知的部分执行不打断 episode；
- 回执区分五种执行状态，并进入结果文件和退出码（a_7、a_8）；
- 仿真和真机行为一致。

**非目标**

- 不做分布式事务，只保证单 episode、单写者、单服务端；
- 读操作不进账本，账本不落盘；
- 不向模型暴露对账工具，也不改 planner 协议；
- **不做按资源调度和后台作业**：服务端写调用本来就是串行的，需要并发的模型推理和 SAM3 已经是独立进程。

## 6. 如何实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1 契约** | 身份字段、`EnvReceipt`、`RequestRejected`、`EnvReceipt → ToolResult` 映射，与 a_5 P1 同一个 PR | 序列化往返一致；五种状态各有断言 |
| **P2 账本** | `ReceiptLedger`、`RpcFacade` 的 `write=True` 登记与钩子 | 同一个 `request_id` 只执行一次；`sequence` 倒退被拒绝且不产生动作；adapter 异常后能查到 `unknown` |
| **P3 客户端与锁存** | reset 分配 `episode_id`、`ExecutionUncertain`、Episode 锁存、自动对账 | 故障注入：执行成功但响应丢失 → 锁存 → 对账得到 `completed` → 解锁，且没有第二次执行；取消产生 `partial` 后写操作仍可用 |
| **P4 切片收口** | 删除 RoboDojo、YAM 等切片里私有的锁存与重试 | 切片私有锁存为 0；dual_franka / YAM 的行为由共享层覆盖并保持一致 |

迁移顺序与 a_5 相同。真机切片最后迁移，默认「不确定即停，等待人工确认」。

## 7. 验收指标

| 指标 | 基线 | 目标 |
|---|---|---|
| 带身份的物理写路径 | 少数（YAM operator receipt） | 100% |
| 共享账本 | 0 | 1 |
| 切片私有锁存 | 3 处以上 | 0 |
| 故障注入：超时后重复执行 | 无用例 | 全部通过，重复执行 0 次 |
| 运行中对账恢复 | 不支持 | 支持 |
| 取消后 episode 仍可继续 | 依切片而定 | 是 |
| 结果文件中的执行状态 | 0 | 100%（a_8） |

## 8. 风险

| 风险 | 对策 |
|---|---|
| 协议变更破坏现有切片 | 按切片开关迁移；`contract_version` 不一致时立即报错 |
| 锁存过于频繁，导致 episode 提前报废 | 发出前的拒绝走 `rejected`；已知的部分执行不锁存；网络抖动做有限次只读重试 |
| adapter 把执行中的异常误报为 `RequestRejected` | 契约测试：`RequestRejected` 只能在第一次原生调用之前抛出 |
| 账本内存增长 | 固定容量加 FIFO 淘汰，淘汰时记日志 |
| 多个客户端写同一个 episode | 视为配置错误，`sequence` 冲突时直接拒绝 |
| 真机安全 | 不确定即停；不自动重试；operator 确认后才能继续 |
