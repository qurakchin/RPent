# a_3 抽出共享工具族
> 状态：草案｜基线 `01e9cb3`｜最后更新 2026-11-14

> 通用动作、感知、记忆、文件工具以包为单位全仓只写一份，各自带评估、可以独立改进，按能力装配；原生技能收敛成 skill binding。
>
> 前置阅读：[a_global](a_global.md) R1/R2/R4/R7/R11；[a_5](a_5_精简机器人接入.md) 的契约；工具包的结构、依赖与安装见 [a_1](a_1_仓库结构、组件边界与安装.md)。

## 1. 问题背景

RPent 的 `@tool` 声明机制本身很好：签名和 Google docstring 生成 schema，参数做 strict pydantic 校验（`extra="forbid"`）。问题在于**实现分布、结果语义和装配方式**。

**同一个动作在各切片里重复实现**（基线中定义该函数的文件数）：

| 工具 | 文件数 | 备注 |
|---|---|---|
| `view_env_state` | 7 | 每个切片都有 |
| `move_to` / `release` | 各 6 | 签名和反馈字段各不相同 |
| `rotate_wrist` | 5 | |
| `back_project` / `_world_from_depth` | 4 / 3 | 坐标约定可能不一致 |
| `query_world_map` | 3 | RoboDojo 用共享版本，RoboTwin 是拷贝，RoboCasa 同名但语义不同 |

以 RoboTwin 为例，`tools.py` 427 行加 `primitives.py` 528 行，其中一半以上是共通动作。

**结果语义混在一个字典里。** `ToolResult(data, images)` 的 `is_error` 只看 `data["error"]`。「参数错误没执行」「执行了但失败」「不确定是否执行」「子目标成功」都用 `error` 或 `success` 表达，planner 无法判断能不能重试。

**装配靠手工拼接。** 每个 toolkit 都用 `iter_tools(...)` + `add_tool` 拼装。能力分支（有无深度、标定、分割，VLA 还是 WAM）散落在注册代码和手写 prompt 里。

**感知工具被拆成原语，编排负担落在 planner。** `segment` 和 `back_project` 在 4–5 个切片里分别定义，但调用记录几乎总是 `segment → 看图选点 → back_project`：前者给出 mask，后者把像素变成世界坐标，合起来才回答「目标在哪」。拆成两个工具后，planner 要在两次调用之间看图、选点、对齐 camera/step/resolution，任何一步错了都表现为「定位不准」，而工具本身没有任何异常。

**工具没有自己的证据面。** 改一个拟合阈值、换一种点选方式，只能看某个 episode 是否成功；失败无法归因到 planner、工具还是环境。`back_project`、`segment` 在 4–5 个切片里各有一份，质量差异也没有共同基线。

**记忆访问没有边界。** 记忆通过通用文件工具读写，`MemoryManager` 的只读和 inbox 权限只在 RPent 自己的文件工具里检查。Claude Code 内置的 `Bash/Write` 和 Codex 的 `full_access` 沙箱都能绕过这层检查。explore prompt 要求写 `corroborations.jsonl`，但除了 prompt 之外，没有任何代码读取它。

## 2. 根因

1. **工具按机器人组织，而不是按能力。** 5 个切片里的 `move_to` 只在控制频率、坐标约定、是否做 yaw 收敛上不同，waypoint、停止判断和反馈完全相同。它本质上是「一份能力实现加少量参数」，却被复制成了 5 个工具。
2. **能力没有单一来源。** 没有一个对象能回答「这个环境应该暴露哪些工具、哪些参数」，所以 schema 无法从能力推导，prompt 也无法按能力过滤。
3. **三类工具混为一谈。** 共享动作应当由能力自动带出；原生技能由模型后端决定是否出现；切片特有工具（如 RoboCasa 的 `navigate_to`）应由切片显式注册。现在三者都只是 `@tool`。
4. **结果类型没有分层。** 调用层、执行层和领域层的信息全压在 `data` 里。
5. **工具按算法原语拆分，而不是按 planner 的问题拆分。** 原语之间的中间结果只对下一个原语有意义，却要求模型承担编排。
6. **工具没有独立评估。** 评估混在 episode 成功率里，无法区分感知误差、策略错误和环境问题；也没有固定输入，改动前后不可比。

## 3. 优秀参考、原则与结构

| URA 做法 | 说明 | 借鉴 |
|---|---|---|
| 工具族目录 | `tools/gripper`、`scene`、`hybrid`、`skills`、`episode`，每个族一个 provider | 按能力分目录 |
| 能力驱动 schema | arm/camera 枚举来自环境描述；有标定才暴露公制开口；`locate` 的方法由深度、标定、SAM 决定 | 能力是 schema 的唯一来源；缺失的能力不暴露 |
| `call_ok` | 发给模型的结果里，`success` 改名为 `call_ok`，只表示调用有效 | 结果分层 |
| 统一运动反馈 | `stop_reason`、`stop_evidence`、位姿误差 | 只统一停止相关字段 |
| Hybrid binding | binding 只做观测编码、预测解码和能力校验，不包含推理和执行循环 | 对应切片的 skill binding（4.7） |
| review 规则 | 集成不得定义模型工具 | 对应 R2 |

**不照搬**：

- `ToolProvider` 继承体系：RPent 用 Protocol 加注册表就够了；
- 手写 JSON schema：RPent 的 `@tool` 更省事，继续使用；
- URA 的 skill library：RPent 的分层记忆更强，这里保留并加上访问边界。

RPent 自己的 PR #341 已经给出工具包形态的实践，可以直接作为参考实现：

| #341 的做法 | 说明 |
|---|---|
| 一个 `geometry` 工具 | 点选、分割、反投影、部件拟合都在工具内部完成；planner 只描述目标与所需量 |
| 显式 observation 契约 | 宿主实现 `ObservationProvider`，提供 RGB、深度或点图、内参与坐标系；工具不猜相机名 |
| 模型客户端外部注入 | grounder、segmenter、`EnvState` 由宿主构造；工具不创建服务、不读环境文件 |
| 独立评估目录 | `toolkits/geometry/evaluation/`：固定清单、独立参考、冻结输入重放、单一报告 |
| 质量与结果分开 | `fit_accepted`、`warnings`、`evidence_status` 与坐标一起返回，警告值不伪装成可用值 |

**原则**：

- 一种能力只有一个工具族实现；
- 一个工具回答 planner 的一个问题，原语是包内实现，不是工具；
- 工具包自带评估，改动在固定语料上比较，而不是靠一次 episode；
- 工具名、schema 和 feedback 由族决定，切片只提供 skill binding 和配置；
- 族之间只通过 `BaseEnvClient`（a_5）和 Episode 会话（a_6）交互。

## 4. 目标设计

### 4.1 结果四层：`rpent/tools/base.py`

只新增以下几个一等字段，领域结果仍然放在 `data` 里，不另设一套 `outcome` 兼容层：

```python
@dataclass
class ToolResult:
    data: dict = field(default_factory=dict)        # 领域结果（不变）
    images: list[bytes] = field(default_factory=list)
    image_labels: list[str] = field(default_factory=list)   # "head_camera@step12"，与 images 一一对应
    call_ok: bool = True                            # 调用是否有效：工具存在、参数合法、框架没有崩
    error: dict | None = None                       # code ∈ {validation, unknown_tool, refused,
                                                    #         execution_failed, execution_uncertain, cancelled}
    no_execution: bool = False                      # 明确没有产生物理动作
    execution_uncertain: bool = False               # 与 a_6 的锁存一致
    execution_status: str | None = None             # 写工具才有：EnvReceipt.status 的原值
```

框架负责统一填充：

- 未知工具、参数校验失败 → `call_ok=False, no_execution=True`；
- 写工具的执行信息来自 `EnvReceipt`（a_5、a_6），由 `BaseEnvClient` 映射：`status` 原样进 `execution_status`；`rejected` / `not_started` → `no_execution=True`；`unknown` 或传输失败 → `execution_uncertain=True`；`executed_steps`、`state_after` 进 `data`；
- 工具抛出其他异常 → `call_ok=False`，`execution_uncertain` 取决于该工具是否已经发出写请求，由 `BaseEnvClient` 判定；
- 发给模型的编码里显式包含 `call_ok`，并在 prompt 片段里说明「`call_ok` 不代表动作成功」（a_2）；
- schema 根节点恢复 `additionalProperties: false`，与 pydantic 的 `extra="forbid"` 保持一致。

### 4.2 能力声明：沿用 `execution_capabilities` dict

```python
# 能力声明沿用现有 execution_capabilities dict：
# env: adapter.describe() 返回的 EnvMeta # a_5 4.2：臂、相机、深度、标定、控制模式
# segmentation: bool                   # 是否连接 SAM3
# policy_backends: tuple[str, ...]     # ("pi05",) / ("fast-wam",) / ...
# real_robot: bool
```

能力只有两个来源：adapter 的 `describe()`（a_5 4.2），以及运行时实际连上的服务。不允许从配置里猜。能力快照写入 `run.json`（a_8）。

### 4.3 工具族、实现位置与工具包

三者的分工（名字与路径以 a_global 2.1 为准）：

| 单位 | 拥有什么 | 位置 |
|---|---|---|
| **工具族** | 模型可见的公共面：工具名、schema、prompt 段、族级结果字段；按能力装配 | `rpent/tools/{scene,motion,memory,file}_tools.py` |
| **轻量实现** | 确定性动作执行器、文件与记忆访问；评估用契约测试和脚本化场景 | 族文件旁，如 `rpent/tools/motion/`（执行器、`vla_act`） |
| **工具包** | 需要独立评估语料的重实现：算法、观测契约、评估 | `toolkits/<name>/`，首个是 `geometry` |

评估跟着实现走：轻量实现的契约测试在 `tests/unit_tests/contracts/`，工具包的语料评估在它自己的 `evaluation/`。族不承担评估，但它的公共面（schema、结果字段）有快照测试。

需要独立评估的共享能力以**工具包**为单位，而不是以一个 `@tool` 函数或一个 `tools.py` 为单位：

```
toolkits/<name>/
  __init__.py
  component.toml     # 可选依赖、导入探针与评估依赖组（a_1）
  tool.py            # planner 唯一入口：@tool 声明、参数校验、结果组装
  core.py            # 算法与状态机，不依赖 rpent 框架
  observation.py     # 输入契约：宿主必须提供哪些观测、标定与坐标系
  prompts.py         # 工具内部调用的模型提示（可选）
  evaluation/        # 固定语料、独立参考、重放、报告
    checklist.py references.py metrics.py replay.py experiment.py report.md
```

PR #341 的文件名是 `geometry_tool.py` / `geometry.py` / `part_geometry.py`，职责分别对应上面的 `tool.py` / `core.py`；迁入时按上面的角色名改名（a_1 4.2 的骨架由 `check_layout` 检查）；`core.py` 太大时可以拆成 `core/` 包。评估里的 `libero.py` 是平台适配，放在 `evaluation/` 内，不属于通用模板。

边界规则：

- 工具包只依赖 `rpent` 的稳定契约（`@tool`、`ToolResult`、`EnvState`、观测协议），**不 import `robots/*`**；grounder、segmenter、observation provider 由宿主构造并注入；
- 工具包不创建进程、不读环境文件、不猜相机名；相机、step、标定和坐标系由宿主提供；
- 工具包的运行时依赖与评估依赖分开声明在 `component.toml` 的 `dependencies` 和 `optional.eval`，安装走具名配方（a_1），不在工具代码里 `pip install`；
- 包内不出现机器人名（R8），平台差异放在 observation provider 和配置里；
- 族的工具包依赖是显式注册，不按名字扫描目录：`SceneTools` 在构造时接收装配层选定的已安装工具包，包名在 `config.py` 和 `component.toml` 中声明；新增工具包必须先在 a_global 2.1 登记，并由使用它的族显式引用。引用发生在构造时而不是模块导入时，所以没装工具包的可选依赖时，基本导入、机器人发现和 CLI help 仍然可用；
- 轻量实现留在 `rpent/tools/`；一旦需要独立评估语料，就升级为工具包。

这条边界让工具可以单独改进：换拟合方法、调质量阈值、改内部点选提示，只改工具包和它的语料，不动任何 `robots/*`；切片只在观测契约变化时改 observation provider。改进是否有效，由工具自己的评估回答（4.5），而不是由某个 episode 的成功与否回答。

族的接口：

```python
class SceneTools:
    def tools(self, caps: dict, cfg: Any) -> Sequence[Tool]: ...          # 按能力裁剪后的工具
    def prompt_sections(self, caps: dict) -> Sequence[PromptNode]: ...   # a_2
    result_fields: type[BaseModel] | None                                # 族级结果字段，供 a_4 渲染
```

工具上下文由 Toolkit 持有并注入（现有实现即 `Toolkit.state` → `EnvState`）：步历史、历史帧与产物引用都从这里读，工具不自己翻输出目录。

| 族 | 对外工具 | 实现位置 | 评估 |
|---|---|---|---|
| **Scene** | `view_env_state`、`geometry`、`query_world_map` | `geometry` 在 `toolkits/geometry/`；其余在 `rpent/tools/scene_tools.py` | `geometry`：冻结 RGB-D、独立参考；其余：契约测试 |
| **Motion** | `move_to`、`move_pose`、`rotate_wrist`、`rotate_pitch`、`set_gripper`、`release`，以及由 skill binding 生成的技能工具（`pi0_pick`、`wam_act`、`rldx_skill`、`lingbot_act`） | `rpent/tools/motion/`（执行器、`vla_act`） | 脚本化场景 + 契约测试 |
| **Memory** | `recall`、`remember`、`corroborate` | `rpent/tools/memory_tools.py`，复用 `MemoryManager` | 权限与合并负例 |
| **File** | `list_dir`、`read_text_file`、`write_text_file`（限定在输出目录内） | `rpent/tools/file_tools.py`（由 `common.py` 拆出） | 路径边界 |

`finish` 依赖运行模式，从 `common.py` 移到 `Toolkit`，由 a_7 的 finish 策略管理；`reset` 属于 episode 生命周期（a_6），本来就不在 `common.py`。文件工具（`CommonTools` → `FileTools`）和 `finish` 搬走后，`rpent/tools/common.py` 删除。切片在 `config.py` 里声明启用哪些族，`Toolkit.add_tools(SceneTools, MotionTools, MemoryTools, FileTools, caps=..., cfg=...)` 负责注册；切片特有工具放在 `native_tools.py` 里显式注册。切片不再需要自己的 `toolkit.py`。

### 4.4 一个工具回答一个问题

判定标准：

- 一个工具对应 planner 的一个问题、一份结果契约、一份评估语料；
- 两个工具如果在调用记录里总是成对出现，且中间结果只对下一个工具有意义，它们是一个工具的内部步骤；
- 原语保留为包内的 Python 函数，不再注册给 planner。

按这个标准重排 Scene：

| 现状 | 回答的问题 | 目标 |
|---|---|---|
| `segment` + `back_project`（+ `sample_world_xyz` 的区域采样） | 「这个目标在哪、多大」 | 合并为 `geometry`：planner 给目标和所需量，工具内部完成点选、分割、反投影与拟合 |
| `view_env_state` | 「现在能看到什么」 | 保留：观测入口，不负责定位 |
| `query_world_map` | 「已知世界地图里有什么」 | 保留为独立工具：数据源、权限和评估语料都不同 |

合并后的 `geometry` 沿用 #341 的结果契约：

- `status` 分 `usable / partial / need_observation / warning / error`；
- 每个字段带 `value`、`unit`、`definition`、`evidence_status`（`measured / inferred / unknown`）和 `source_refs`；
- 返回 `pixel_rc`，让 planner 知道工具选了哪个像素；质量不过关时返回 `fit_accepted=false` 和 `warnings`，而不是把警告值伪装成可用值。

`segment`、`back_project`、`sample_world_xyz` 不再出现在工具列表，但保留为包内函数和宿主 observation provider 的实现细节；Flash replay、手工脚本和评估管线继续直接调用这些函数。

输入有两条路径，用同一套评估对照：

- `query`：planner 描述目标，工具调用注入的 grounder 选点。适合没有精确像素的场景，也是 #341 的默认路径；
- `pixel`：宿主或 planner 已经选定像素（例如 LIBERO 的高清图流程），工具跳过 grounding。没有 Molmo 的切片也能用。

迁移时先改 prompt：把「看高清图选像素，再调 `back_project`」改成「描述目标和所需量，调用 `geometry`」。`geometry` 的 schema 快照、prompt 片段和 LIBERO 试点在同一个 PR 里更新（a_2、a_9）。

Motion 暂不合并：`move_to` 与 `move_pose` 回答不同的问题（到达目标 vs 相对位姿），各自有独立参数和停止语义；它们共享执行器和停止反馈即可。文件与记忆工具同理，按问题而不是按函数合并。

### 4.5 工具独立评估

工具能不能单独改进，取决于它有没有独立于 episode 的证据面。评估不是单测的替代品：单测证明契约，评估测量质量。

| 组成 | 要求 | #341 的做法 |
|---|---|---|
| 固定语料 | 固定任务、seed、相机、step 与目标部件；语料有版本和 hash | 16 个 LIBERO 任务 × seed 1–5 = 80 cases / 160 measurements |
| 冻结输入 | 保存 RGB-D、标定、点选与 mask，重放不再调模型 | `infer --replay` 只读冻结观测 |
| 独立参考 | 参考来自网格几何和同帧 FK，绝不来自工具输出、mask 或点选 | `references.py` 在预测全部保存后才读取 |
| 可重放 | 工具与语料的 commit/hash 写进 manifest；输出目录必须是新的 | `run_manifest.json` + `report.md` |
| 报告 | coverage（返回/全部）、mean/median/max、按质量分组、per-target、provenance | accepted / warning 分组，warning 单列 |
| badcase | 每个失败有 case id、期望/实际、根因、修复与回归归属 | 语料版本升级或新增单测 |

三条纪律：

1. **不重跑旧预测。** 每次评估从冻结输入重新计算，不能把上一次的坐标拼进结果，否则无法判断改动是否有效。
2. **不只报均值。** 尾部误差、拒答率、`warning` 比例和 coverage 一起报。`geometry` 的基线就是例子：160 个请求全部返回，均值 21.3 mm，但 accepted 只有 18 个（均值 2.2 mm）；只报均值会掩盖大部分结果未通过质量检查。
3. **不把评估当成功率。** 评估测的是工具在一个固定输入集上的输出质量；它不证明 planner 会用，也不证明真机可用（a_global 5.2）。

改进闭环：

```
真实 badcase → 归因（点选 / 分割 / 反投影 / 拟合 / 结果契约）
            → 修复 + 同一语料前后对比
            → 进入下一语料版本或回归测试
            → 报告保留单一当前基线
```

一条 badcase 记录至少包含（下面是格式示例，不是实际结果）：

```
case_id:   <suite>_t<task>_s<seed> / <quantity>
expected:  <独立参考值>
returned:  <返回值或 null + 状态>
cause:     <点选 / 分割 / 反投影 / 拟合 / 契约>
fix:       <改了什么，哪些情况仍然拒绝>
regression: <下一版语料 case 或单测名>
```

语料变更必须升版本，旧报告不与新语料直接比较；删除 case 要在 PR 里说明原因。工具改动 PR 的证据段（a_0 4.3）附上命令、语料版本和前后对比表；均值或尾部变差要有解释，不能只报改善的子集。

分层要求，避免每个工具都被迫建 benchmark：

| 工具类型 | 评估形式 |
|---|---|
| 感知、估计、有模型参与 | 固定语料 + 独立参考 + 冻结输入重放（必须） |
| 确定性动作 | 脚本化场景 + 契约测试 + 停止/误差统计 |
| 文件、记忆 | 权限与合并负例 + 契约测试 |

新增一个工具包时，最小评估清单是：一个真实平台的 3–5 个固定 case；保存 RGB-D、点选与 mask；一个独立参考来源；一条能写出 `report.md` 的 `evaluate` 命令；一个已知 badcase。先有这五项，再扩语料，不为新工具先建平台。

评估代码放在 `toolkits/<name>/evaluation/`，快速检查放在 `tests/unit_tests/toolkits/<name>/`。全量评估不挂在每个 PR 上：PR 跑小集或重放，全量在 nightly 或工具改动时手动触发。运行产物和原始数据放在源码树外（`GEOMETRY_RUN_DIR` 这类目录），报告只保留当前基线。

### 4.6 Motion：统一运动执行与反馈

客户端负责 waypoint 插值、进度停止判断和跳变检测，服务端每次只执行一个语义命令。每个运动工具返回同一组停止字段：

```
stop_reason: arrived | stalled | diverging | unsafe_motion | planning_rejected | max_steps | episode_over
stop_evidence: {...}                    # 末步误差、窗口改善量、跳变幅度
pose_error: {"pos_m": ..., "ori_rad": ...}
executed_steps: int
```

控制频率、步长上限、是否做 yaw 收敛等参数来自切片配置，不在工具参数里暴露。

### 4.7 VLA/WAM：模型服务、技能绑定与执行循环

原生技能拆成三段，各有唯一位置（a_global 2.1）：

| 段 | 位置 | 负责 | 不负责 |
|---|---|---|---|
| 模型服务 | `capabilities/<name>/`，基类在 `capabilities/_base/` | 能力契约输入（`am_contracts`）↔ 模型张量（`adapter/encode.py`、`decode.py`）、推理、序列化、超时 | 机器人观测格式、判据 |
| 技能绑定 | `robots/<name>/skills/<skill>.py` | 机器人观测 → 能力契约输入；动作块 → `NativeChunk`；工具参数 schema；子目标判据 `judge` | 推理、执行循环 |
| 执行循环 | `rpent/tools/motion/vla_act.py` | 采集 → 绑定编码 → 推理 → 绑定解码 → 逐块执行（每块一个回执，a_6）→ `judge` → 存档 | 解释判据 |

```python
class SkillBinding(Protocol):            # 每个切片的 skills/<skill>.py 实现
    name: str                            # 工具名：pi0_pick / wam_act / ...
    capability: str                      # 用哪个 capabilities/<name>
    def schema(self) -> type[BaseModel]: ...                       # 只含 prompt、max_chunks 等预算参数
    def encode(self, frames: dict, state: EnvSnapshot, instruction: str) -> AMRequest: ...
    def decode(self, response: AMResponse, state: EnvSnapshot) -> NativeChunk: ...
    def judge(self, before: EnvSnapshot, after: EnvSnapshot, criteria: dict) -> dict: ...  # 阈值来自 config（a_7）
```

- 现有切片里的 `vla_client / vla_server / wam_client`（平台传输，如 LingBot 的 WebSocket、RLDX 的会话）并入技能绑定，不删除；
- `judge` 只代表子目标，不在模型 client 基类里；
- 绑定不支持子指令时（例如 RoboTwin 的 LingBot），schema 里不出现 `prompt` 参数，而不是收下参数后悄悄忽略。

### 4.8 Memory：带边界的分层记忆

保留现有的 `MemoryManager`、分层结构（global / task-family / task-specific）、合并和 HF 版本化语料，只改变**访问方式**：

| 工具 | 行为 | 现状问题 |
|---|---|---|
| `recall(scope, path=None)` | 不带 path 时列出该 scope 的条目，带 path 时读取内容；读取范围由 `MemoryManager` 按配置裁剪，例如 RoboCasa 只读当前任务；每次读取都写入审计 | 现在依赖通用文件工具，审计只有 RoboCasa 有 |
| `remember(kind, text, evidence)` | 在 inbox 写一份草稿，frontmatter 当场校验 | 现在由模型手写 YAML，合并时才发现格式错误 |
| `corroborate(note_id, cell, verdict)` | 记录佐证，由 `merge_memory` 消费并更新 confidence | 现在 `corroborations.jsonl` 没有任何读取方 |

配套措施：

- Claude 后端加 `can_use_tool` 钩子，Codex 改用 `workspace-write` 沙箱，禁止内置的 Bash/Write 修改记忆目录；
- 通用 File 工具不再能访问记忆目录。

## 5. 目标与非目标

**目标**

- 通用动作、感知、记忆访问全仓各一份，以工具包为单位实现，按能力自动装配，切片里没有能力分支；
- 感知工具只有一个 planner 入口，`segment` / `back_project` 这类原语不再单独暴露；
- 每个共享工具有明确的所有者和独立评估入口，感知工具能在冻结输入上重放；
- 工具改动能在同一语料上给出前后对比，badcase 有回归归属；
- 结果四层显式表达，schema 可以快照；
- 原生技能统一走 skill binding + `vla_act`，判据和 chunk 语义不变；
- 记忆权限对所有写入路径生效，佐证（corroboration）真正参与合并。

**非目标**

- 不重写 `@tool`；除把 `segment` / `back_project` 合并为 `geometry` 外，不改现有工具名；
- 不引入 provider 继承体系；
- 不为每个工具建立 benchmark：动作、文件、记忆工具用场景与负例测试；
- 不在每个 PR 跑全量评估；
- 不把评估指标当唯一合并标准，coverage、拒答和 `warning` 比例同样要看；
- 不强制所有工具共用结果字段；
- 不统一领域 feedback，只统一停止相关字段；
- **不做后台作业和按资源调度**：env 是单进程，写调用本来就串行，Toolkit 现有的「readonly 并发 + 写者优先」已经够用；
- **不做语义地图、向量检索，也不提供给 agent 的 `forget`**：目前没有使用方；遗忘通过合并规则和人工审阅完成。

## 6. 如何实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1 结果四层** | `ToolResult` 新字段、框架填充规则、`additionalProperties: false` | 现有工具全部通过契约测试；参数错误不再表现为领域失败 |
| **P2 能力与装配** | `execution_capabilities`、`SceneTools / MotionTools / MemoryTools / FileTools`、`add_tools`；`finish` 移入 `Toolkit`，`reset` 由 episode 生命周期提供 | 同一切片在有、无深度两种配置下，工具列表随之变化；切片代码里没有 `if has_depth` |
| **P3 感知工具合并** | `segment` + `back_project`（+ `sample_world_xyz` 区域采样）合并为 `geometry`，原语留在包内；`query_world_map` 的切片拷贝合并为一份；File 工具限定在输出目录 | planner 工具列表里没有 `segment` / `back_project`；切片内实现为 0；schema 与 prompt 快照同步 |
| **P4 工具评估** | `toolkits/geometry/evaluation/` 的固定语料、独立参考、冻结输入重放与报告；登记首批 badcase；评估依赖进入 `component.toml` 的 `eval` 组 | 80 cases 能在 CPU 上重放；报告含 coverage 与分组误差；一个真实 badcase 走完闭环；`geometry-eval` 配方可单独安装 |
| **P5 Motion** | 统一运动执行器和反馈 | `move_to`、`release`、`set_gripper`、`rotate_wrist` 在切片里的实现为 0 |
| **P6 技能绑定** | `vla_act` runner，各切片实现 skill binding | `pi0_pick`、`wam_act`、`rldx_skill`、`lingbot_act` 的判据和 chunk 语义通过 parity 测试 |
| **P7 Memory** | 三个记忆工具、内置工具限制、合并时消费佐证 | 用内置 Bash/Write 写记忆目录被拒绝；佐证能改变 confidence |

P1 和 P2 可以并行。P3 和 P5 依赖 a_5 的观测契约；P4 依赖 P3。P6 依赖 P5 和 a_6 的回执。P7 与其他阶段独立。

切片随 `env_contract=v2` 切换到工具族；旧工具在该切片通过 parity 之前保留，开关回退时一并生效（a_global 5.3）。parity 通过后删除切片内的旧实现，不新增开关。

## 8. 风险

| 风险 | 对策 |
|---|---|
| 过度统一，把领域 feedback 也强行对齐 | 只统一停止字段，领域诊断留在 `data` |
| `call_ok` 改变模型的判断 | prompt 片段说明其含义；schema 快照加固定 seed 冒烟验证 |
| 能力声明与实际不符 | 能力只来自 adapter 和已连接的服务；写入 `run.json`，便于发现不一致 |
| runner 吞掉技能判据 | `judge` 归 skill binding 所有，runner 不解释判据 |
| 记忆工具改变探索行为 | 先在 LIBERO 的 explore 模式对照记忆产出（条目数、合并冲突数）；prompt 的记忆协议同步迁移（a_2） |
| 收紧内置工具影响 planner 的其他能力 | 只限制记忆目录和仓库源码目录的写入；读取和输出目录不受影响 |
| 评估语料维护成本高 | 固定清单加自动报告；语料变更走版本，不随手加 case |
| 在语料上过拟合 | 保留新 seed 或新任务作留出集；报告 coverage 和尾部误差，不只看均值 |
| 评估变成形式 | 必须写前后对比和 badcase；只报通过子集视为未验证 |
| 合并工具改变 planner 行为 | 先在 LIBERO 试点；prompt、schema 快照和 parity 同 PR；两条输入路径用同一语料对照 |
| 工具包变成新的单体 | 包只依赖稳定契约；轻量工具不升级为包；包之间不互相 import |
