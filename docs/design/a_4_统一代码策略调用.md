# a_4 统一代码策略调用
> 状态：草案｜基线 `01e9cb3`｜最后更新 2026-11-13

> 代码模式只是同一批工具的另一种调用方式：在核心里只接一次，切片不需要为它多写一行。
>
> 前置阅读：[a_global](a_global.md) R1/R2/R5/R8；[a_2](a_2_拼装提示词.md)、[a_3](a_3_抽出共享工具族.md)、[a_7](a_7_隔离任务真值.md)。
> 参照：RLinf/RPent PR #340（open，`--policy-mode code`）。

## 1. 问题背景

PR #340 给 RPent 加了代码策略模式：planner 在持久化的 Python cell 里调用 `robo.<tool>(**kwargs)`，用循环和条件把多个原语组合起来，按数值反馈闭环控制。

运行时设计扎实，值得保留：

- `CodeSession` 和 worker 是独立进程，变量在 cell 之间保留；
- 每个 cell 有 120 s 墙钟上限，最多 100 次工具调用；
- 超时或取消时只丢弃命名空间，不重放已经执行的动作；
- 机器人调用仍然经过原 toolkit 的调度器，保留校验、观测采集和取消语义。

问题出在它与切片的接法上。

| 现象 | 证据（PR #340） |
|---|---|
| 每个切片各加一份代码模式 prompt | `robots/*/prompts/code_policy.py` 共 7 份、794 行（RoboCasa 234 行、RoboTwin 194 行、LIBERO 141 行……） |
| 切片 prompt 重新描述工具语义 | 例如 RoboTwin 的「`move_to` 指向 EEF，TCP 在 approach 方向再往前 0.12 m」、夹爪取值、`step_lim` 计数，与工具描述和工具模式下的 prompt 各说一遍 |
| 教模型读真值 | RoboTwin 的代码模式 prompt 写着「Only the native `eval_success` flag proves task success」 |
| 代码模式下没有记忆 | `CodePolicyTools` 排除了 `MEMORY_TOOLS`（三个通用文件工具）；LIBERO 在代码模式下关闭了 local memory；共享 prompt 写着「Do not retrieve a task-memory corpus in this mode」 |
| 核心里写死了工具名 | `OPERATOR_TOOLS = {"request_scene_reset", "request_operator_verdict"}` |
| 每接一个切片要改 4 个文件 | 7 个切片的 `robot_spec`、`toolkit`、`prompt_bundle`、`prompts/code_policy.py` 都被改了；dual_franka 还专门加了一个 `observe` 工具 |
| 返回字段只能靠 prompt 描述 | API reference 只列出入参 schema；`observation["log"]["result"]` 这类返回结构写在切片 prompt 里 |

## 2. 根因

1. **代码模式被接在了切片和 prompt 这一层，而不是工具层。** 工具语义由切片自己描述，所以每多一种调用模式，就要在每个切片里再描述一遍。这和 a_5 里「抽象轴选错」是同一个问题。
2. **结果结构不是契约。** 返回值没有统一的形状（a_3 的四层结果加上族级反馈字段），API reference 自然没法自动生成「返回什么」，只好由人手写。
3. **记忆访问依赖通用文件工具。** 给代码 cell 开放文件工具等于开放任意文件访问，只能整体关掉，代码模式因此失去了 RPent 最重要的能力之一。
4. **工具特性靠名字识别。** 「会等待 operator」本应是工具的元数据，现在却在核心里按名字特判。

## 3. 优秀参考、原则与结构

URA 的 Code-as-Policy（`context/code_as_policy.py`、`execution/code_as_policy/`）：

| 做法 | 说明 | 借鉴 |
|---|---|---|
| API 文档由会话中的真实 schema 生成 | `robot_api.md` 包含描述、入参 schema，以及从 pydantic 结果模型（`ResultFields`、`MotionFeedback`）生成的**返回字段表** | 返回结构也自动生成 |
| bridge 复用同一个 executor | 脚本调用经由 `ToolClient`，进入同一套资源策略和校验 | 已有（#340），保持 |
| 传输错误时不重放 | 提示「Execution may have occurred; do not replay」，并撤销 bridge | 对接 a_6 的不确定态 |
| 可信的 finish 回执 | agent 是否完成，以真实的 finish 回执为准，不看 SDK 里的 finish 提议 | 对接 a_7 |
| 不支持的后端在配置阶段拒绝 | 不在运行中途才失败 | 保持 |

**原则**：

- 一份工具声明对应两种调用方式，参数、返回、错误和图像完全一致；
- 代码模式在核心中只接入一次；
- 切片的领域知识由两种模式共用；
- 真值隔离、回执语义和记忆边界在代码模式下同样生效。

## 4. 目标设计

### 4.1 核心唯一接入点

```
CLI --policy-mode tool|code
          │
   get_toolkit(...)  ← 切片不感知调用模式
          │
   code 模式：CodePolicyTools(toolkit)   # 来自 #340，核心包装任意 toolkit
          │
   prompt：base → mode_code → families → domain（与 tool 模式共用）
```

- 是否启用代码模式只由 CLI 决定；切片的 `robot_spec`、`toolkit` 和 `prompt_bundle` 都不需要修改；
- 不支持代码模式的 planner 或机器人，在配置阶段直接拒绝。

### 4.2 API reference 包含返回结构

`code_policy_api_reference(tools)` 在现有入参 schema 的基础上增加两部分：

- **通用返回结构**：四层字段（`call_ok`、`error`、`no_execution`、`execution_uncertain`）加 `data`，在 `mode_code` 片段里统一说明一次；
- **族级返回字段**：每个工具族声明自己的结果模型（例如 Motion 的 `stop_reason`、`stop_evidence`、`pose_error`、`executed_steps`），由 reference 自动渲染成字段表。

这样切片 prompt 里不再需要写 `observation["log"]["result"]` 之类的结构说明。

### 4.3 领域知识两种模式共用

- 删除 `robots/*/prompts/code_policy.py`；
- 坐标约定、任务族、失败模式等内容写在切片的 `prompts/domain.py` 里，两种模式共用（a_2）；
- 确实只适用于代码模式的领域约定（例如「接触前每 5–10 mm 检查一次」），作为 domain 中带 `modes={"code"}` 标记的一小段，不单独成文件；
- 像 TCP 偏移 0.12 m 这类原生差异，交给 adapter 换算（a_5），从 prompt 中删除。

### 4.4 安全语义在代码模式下同样生效

| 语义 | 在代码模式中的表现 |
|---|---|
| 真值隔离（a_7） | 结果经过同一层过滤，`robo.view_env_state()` 返回的内容里没有 `eval_success` 和 `terminated`；prompt 不再引用它们 |
| 不确定态（a_6） | cell 内出现 `execution_uncertain` 时，抛出 `ToolCallError`（附带结果），cell 中止；锁存在 episode 层，之后 `robo` 的写调用返回 `no_execution`；cell **不会**自动重跑 |
| 记忆（a_3） | Memory 族的 `recall / remember / corroborate` 作为普通工具暴露给 `robo`；通用文件工具继续排除在外 |
| 等待 operator | 改为工具元数据 `waits_for_operator=True`，由框架决定把它作为顶层工具暴露，删除核心里的 `OPERATOR_TOOLS` |
| 事件（a_8） | cell 内的每次工具调用都照常发出 `tool_call`，事件中附带 `cell_id` |
| 运行结果 | `run.json` 记录 `policy_mode`；agent 是否完成以可信的 finish 回执为准 |

## 5. 目标与非目标

**目标**

- 新机器人接入代码模式无需改动任何文件；
- 切片中代码模式专用的 prompt 文件数为 0；
- 代码模式与工具模式对同一调用返回同一个结果；
- 代码模式也能用记忆，真值同样不可见。

**非目标**

- 不重写 #340 的运行时（`CodeSession`、worker、预算、超时）；
- 不把 worker 当作安全沙箱，如实说明它只限制工作目录和调用预算，不是 OS 级隔离；
- 不新增工具实现，也不新增迁移开关：`--policy-mode` 是运行配置；
- 不默认启用代码模式，Flash 也不走代码模式。

## 6. 如何实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0 合入 #340 运行时** | 保留 `rpent/code_policy/` 和 `rpent/prompt/code_policy.py`；切片 prompt 暂时保留 | 现有生命周期测试通过 |
| **P1 核心唯一接入** | CLI 统一包装；撤销切片 `robot_spec`、`toolkit` 中与代码模式相关的改动；用 `waits_for_operator` 元数据取代 `OPERATOR_TOOLS` | 不修改切片也能对任一切片启用代码模式；核心代码中不再有工具名特判 |
| **P2 返回结构入 reference** | 族结果模型加四层字段说明（依赖 a_3 P1、P4） | API reference 中能看到返回字段表 |
| **P3 切片 prompt 收口** | `code_policy.py` 并入 domain；删除重复的工具语义和真值引用（依赖 a_2、a_7） | 7 份 794 行降为 0 份；代码模式的 prompt 快照中没有 `eval_success` |
| **P4 记忆接入** | Memory 族工具在代码模式下可用；LIBERO 代码模式恢复 local memory（依赖 a_3 P6） | 代码模式下的记忆读取写入审计日志 |
| **P5 一致性测试** | 同一个 scripted 序列分别走 tool call 和 `robo.<tool>()` | 两种模式的结果与 step 序列一致（a_9） |

## 7. 验收指标

| 指标 | 基线（#340） | 目标 |
|---|---|---|
| 切片中代码模式专用的 prompt | 7 份 / 794 行 | 0 |
| 新切片启用代码模式需要改的文件 | 4 个 | 0 个 |
| 核心中的工具名特判 | `OPERATOR_TOOLS` | 0 |
| 代码模式中模型可见的真值字段 | 有（`eval_success`） | 0 |
| 代码模式能否使用记忆 | 否 | 是 |
| 两种调用模式的结果一致性 | 未测试 | parity 测试通过 |

## 8. 风险

| 风险 | 对策 |
|---|---|
| 删掉切片 prompt 后，代码模式的效果下降（#340 的 LIBERO-PRO 结果依赖这些 prompt） | 先把有效内容迁入 domain 和工具族描述，再删除；用 #340 的评测设置做前后对照 |
| 开放记忆后，代码模式行为发生变化 | 先在 LIBERO 上对照「有记忆 / 无记忆」两种设置，再决定默认值 |
| 把 worker 误当成沙箱 | 在 `mode_code` 片段和文档中明确说明它不是安全边界；凭据不注入 worker 环境 |
| cell 中途出现不确定态，模型又写一个 cell 绕过 | 锁存在 episode 层，新的 cell 同样拒绝写操作 |
