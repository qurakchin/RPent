# a_0 建立文档纪律与评审闸门
> 状态：已实施（P1–P5）；P6 发布清单已落地，尚未演练｜基线 `b4d8459`｜最后更新 2026-11-13

> URA 的工程质量不只来自代码：它把每条工程判断写成可引用的文档，把每次变更的证据写进评审。本文先调研 URA 的做法，再说明 RPent 已有的基础、真实缺口和移植方案。
>
> 前置阅读：[a_global](a_global.md) 第 3、4 节；[a_9](a_9_建立验证护栏.md)。

## 1. 问题背景

改造前，RPent 的规则并不少：`AGENTS.md` 65 行、`CONTRIBUTING.md` 207 行、`docs/STYLE_GUIDE.md` 353 行、四份 `.agents/skills/` 任务手册、`tests/README.md`、PR 模板和五条 CI workflow。问题不是「没有规范」，而是规范没有形成可执行、可核对的闭环。

| 现象 | RPent 基线 | URA 做法 |
|---|---|---|
| 规则入口 | `CLAUDE.md` 是指向 `AGENTS.md` 的符号链接；脱离 Unix 符号链接或导出 tar 时入口失效，规则归属也不显式 | `CLAUDE.md` 只有一行 `@AGENTS.md` |
| 规则分布 | CONTRIBUTING、STYLE_GUIDE、skills 各写一部分，同一约束重复 | 每类规则只有一个权威文件，其余链接 |
| 设计文档 | a_1–a_9 在仓库外（`~/Works/rpent_design`），评审看不到 | 架构、开发、集成文档都在 `docs/`，随 PR 修改 |
| 文档状态 | 机器人页只有 `coming soon` 这类页面级标记；没有「已验证 / 未验证」的统一段落 | 每篇集成指南有 `## Validation status`，写日期、commit、硬件、seed |
| 证据格式 | PR 模板只有 Testing / Manual verification，没有「没证明什么」 | PR 的 Validation 分段列证据，末尾写 Limitations |
| 变更 → 证据 | 分散在 CONTRIBUTING 和 `verify-change` skill | `docs/development.md#validation-and-review` 一张表 |
| 发布 | 仓库没有发布 workflow，步骤只存在于个人经验 | `release.yml` 加 `publishing.md`，显式发布 |
| 图示 | 架构图外链到另一个仓库的 PNG | 图有 HTML 源、PDF 和导出脚本 |

后果有两层：

- **设计无法被引用**：改造方案写在仓库外，PR 评审只能就代码论代码；
- **「已验证」没有共同含义**：单测通过、仿真跑通一次、真机完成一次，在 PR 里都可能被写成「测试通过」。

a_9 解决「规则会被测试住」，本文解决「规则和证据会被写住」。

## 2. 根因

1. **规则按文件生长，而不是按读者和一次变更组织。** 同一约束被复制到多处，改动时只更新一处，剩下的变成错误信息。
2. **文档写作与代码评审是两条流程。** 设计文档不在仓库，就不进入评审，也不会随实现更新。
3. **只要求「要验证」，没规定证据的形状和级别。** 评审无法核对，也无法阻止把一次结果外推成结论。
4. **缺少「未验证」的合法措辞。** 作者倾向于把一次成功写成「支持」。
5. **发布与文档同步靠记忆。** 没有闸门、清单和可独立执行的步骤。

## 3. URA 的做法

URA 公开树（基线 `852518e`）没有 `tests/`，验证靠 `scripts/validation/` 与人工评审。它的质量优势来自三件事：规则单一来源、文档按读者分层、证据写进变更流程。

### 3.1 规则只有一个来源

- `AGENTS.md` 91 行，分四段：改代码前做什么、架构与扩展点、兼容与验证、Code Review Rules；
- `CLAUDE.md` 全文只有 `@AGENTS.md`，不存在第二份规则；
- `CONTRIBUTING.md` 只讲流程和检查命令，并指向 AGENTS 与 `docs/development.md`；
- `docs/development.md` 用 `Owns / Keep out` 表规定每个目录负责什么、禁止放什么。

它还明确划清了一条容易被忽视的边界：**开发指令不是机器人 prompt**。`AGENTS.md` 开头声明本文不适用于 episode；`docs/development.md` 末尾单列一节点明，在 checkout 里新增指令文件会改变 coding agent 的有效上下文，不能把「加了文档」当作「运行时行为不变」。

### 3.2 文档按读者分层

| 文档 | 读者 | 回答的问题 |
|---|---|---|
| `README.md` | 使用者 | 是什么、怎么开始 |
| `docs/README.md` | 使用者与开发者 | 从哪篇读起（Get started / Run and inspect / Understand and extend） |
| `docs/architecture.md` | 理解系统的人 | 设计原则、执行流、模块职责、共享工具与 episode 所有权 |
| `docs/development.md` | 扩展者 | 代码放哪、边界是什么、改动需要什么证据 |
| `docs/<integration>.md` | 接环境的人 | 运行时准备、命令、观测、判定与验证结果 |
| `SOURCE.md` | 维护者 | 上游 pin、来源与授权 |
| `CHANGELOG.md` | 用户 | 用户可见变化、限制、协议兼容 |
| `docs/pypi.md` | PyPI 访客 | 安装与快速开始（嵌入包元数据） |

每篇文档开头用一句话说明职责；同一内容不重复写第二遍，而是链接到拥有它的那篇。`docs/development.md` 还有一张「想改 X，从这开始，守住什么边界」的对照表，把读者的问题直接映射到文件和边界。

### 3.3 证据写进变更流程

`docs/development.md#validation-and-review` 给出一张变更类型到证据的表：分层/导入、环境协议/生命周期、共享工具/感知、planner/provider、打包/依赖、仅文档。仅文档也要验证路径、链接、命令和与契约的一致性。

PR 描述的事实模板（从 #20、#23、#24、#29 归纳）是：

```
Problem → Change → Validation → Limitations（+ Migration）
```

Validation 的写法有明确要求：

- 写数量和命令，例如「375 CPU checks 和 21 subchecks 通过，3 项可选跳过」；
- 分开列证据级别：CPU 契约、native 仿真、真机；
- 单次结果不外推，例如「这是一次 episode，不是成功率」；
- 失败照实写，例如 BEHAVIOR 的 native 结果是 unsuccessful，记录后另列修复验证；
- 说明「CPU checks 不构成真机证据」，CHANGELOG 条目同样带这个限定。

`AGENTS.md` 的 Code Review Rules 不是抽象原则，而是具体反模式清单：integration-local model tools、通用 `execute_tool(name, args)` 路由、tool family 反向依赖原生集成、重复 episode 状态、向 planner 宣称不支持的能力、SDK 决策进入通用调度、UI/telemetry 里实现机器人控制。

### 3.4 发布是显式闸门

URA 的 `.github/workflows/release.yml` 把「检查」和「发布」分开：

- PR 与 main push 只构建、安装校验（Linux Python 3.11/3.12、macOS、pip/uv、升级、运行时依赖契约）；
- 上传只在 `workflow_dispatch` 选 PyPI/TestPyPI 且 ref 是 tag 时发生；
- 发布 job 用 Trusted Publishing，构建 job 只读，凭据不经过源码目录；
- `docs/publishing.md` 把流程拆成「准备 → 最终确认 → 显式发布 → 验证」，并写明哪些动作不会发布。

RPent 本次只落地可执行的发布清单（`docs/releasing.md`），不新增 release workflow；两者的取舍见 §9。

### 3.5 文档资产可复现

架构图目录同时放 HTML 源、矢量 PDF 和 PNG，README 写清画布尺寸，并提供导出脚本；改图时要求三者同步。这保证图不会变成无法更新的截图。

### 3.6 可以提炼的原则

- 一条规则只有一个权威位置，其它文件只引用；
- 每份文档写清读者、职责和不负责的内容；
- 证据必须可定位：命令、commit、环境、结果，以及「没证明什么」；
- 文档描述当前行为，历史进 release note 或迁移说明；
- 闸门分级上线：先 warning，再 error。

## 4. 目标设计

### 4.1 规则分层与单一事实源

| 文件 | 读者 | 唯一职责 | 不写什么 |
|---|---|---|---|
| `AGENTS.md` | 开发 agent、贡献者 | 操作规则：改代码前后做什么 | 架构解释、命令清单 |
| `CLAUDE.md` | Claude Code | `@AGENTS.md` 一行 | 任何规则正文 |
| `CONTRIBUTING.md` | 人类贡献者 | 流程、环境、检查命令、PR 要求 | 架构边界 |
| `docs/STYLE_GUIDE.md` | 文档作者 | 页面结构、语言、导航 | 代码规则 |
| `docs/.../development/` | 扩展者 | 组件边界与扩展步骤 | 操作流程 |
| `docs/design/a_*.md` | 改造参与者 | 为什么改、改成什么、如何验收 | 用户教程 |
| `.agents/skills/*` | 执行具体任务的 agent | 任务手册与检查清单 | 新的规则来源 |
| `tests/README.md` | 测试作者 | 测试布局与运行方式 | 验证口径 |
| `CHANGELOG` / release notes | 用户 | 可见变化与限制 | 设计论证 |

判定方法：同一句话如果出现在两个文件里，保留在职责最接近的那个，另一个改成链接。

### 4.2 设计文档入库

- 新增 `docs/design/`，存放 a_0–a_9、`a_global`、`a_summary` 与 `assets/*.svg`；
- 每篇开头加状态行：`状态：草案 | 部分实施 | 已实施`、基线 commit、最后更新日期；
- 设计变更走 PR，与实现同一个评审流程；
- 实施完成后，把「目标设计」改写成当前行为，删掉已被取代的段落；历史由 git 保存，不在文档里堆版本。

### 4.3 PR 证据契约

把 URA 的事实模板写进 `.github/PULL_REQUEST_TEMPLATE.md`：

```markdown
## Problem
## Change
## Contract and migration
## Validation
- CPU:
- 仿真:
- 真机:
## Limitations
```

规则正文在 [CONTRIBUTING 的「Validation evidence / 验证证据」](../../CONTRIBUTING.md#validation-evidence)一节；PR 模板、`verify-change` 和 `review-pr` 只引用它。设计意图是：证据按 CPU、仿真、真机分档，每档可定位到命令或产物；单次结果不外推；最后必须回答「这次没有证明什么」。具体写法、例外和针对工具、依赖、行为保持型重构的专门要求都以该节为准。

### 4.4 文档状态词汇

状态词表由 [docs/STYLE_GUIDE.md#validation-status](../STYLE_GUIDE.md#validation-status) 维护，当前为「已验证（多次）」「已验证（单次）」「外部结果」「仅 CPU」「未验证」「实验性」「不适用」。设计约束是：任何「支持 / 可用 / 兼容」的表述都要能对上其中一行；对不上就降到「未验证」；论文或第三方结果标为「外部结果」，不写成「已验证」。

### 4.5 评审闸门

| 闸门 | 检查什么 | 形式 |
|---|---|---|
| 人评审 | 责任层、契约与迁移、证据是否匹配变更、文档是否同步 | `review-pr` 清单 |
| 机器 | 格式、单测、布局、schema/prompt 快照 | `pre-commit`、`unittest`、`check_layout`（a_9） |
| 文档 | 链接、命令、状态词；与实现一致 | `docs-check` 自动检查可判定项，人工核对语义 |
| 发布 | 版本与 tag 一致、构建可复现、显式触发 | 发布清单；本仓库不新增发布 workflow（见 §9） |

人工评审不能省；机器闸门只负责可判定的部分。

### 4.6 图示与命名

- 设计图和架构图入库，保留源文件（SVG）和生成方式；
- 图中的组件名必须与代码标识符一致，不使用比实现更强的词（例：用「拼装」而不是「编译」，见 a_2）。

## 5. 目标与非目标

**目标**

- `CLAUDE.md` 不含规则正文，只有 `@AGENTS.md`；
- 每个 PR 都能看到三级证据与 Limitations；
- 每个机器人 / 仿真文档都有状态与证据段；
- 设计文档在仓库内，评审可以直接引用；
- 文档-only PR 也检查链接、命令和命名。

**非目标**

- 不引入新的文档站点或静态检查框架，沿用 Sphinx、pre-commit 和现有 skills；
- 不追求文档覆盖率、字数或每页都有图；
- 不要求每个 PR 跑 benchmark、GPU 或真机；
- 不改 `review-bot` 的实现，只给它补输入规范；
- 不建立第二套规则副本，也不新设「文档委员会」式流程。

## 7. 验收指标

| 指标 | 基线 | 目标 |
|---|---|---|
| `CLAUDE.md` 中的规则正文行 | 符号链接，无独立正文 | 0（仅 `@AGENTS.md`） |
| PR 描述含三级证据与 Limitations | 部分 | 100% |
| 有状态与证据段的机器人 / 仿真文档 | 0 | 全部 |
| 仓库内设计文档 | 0 篇 | a_0–a_9 加两篇汇总 |
| 文档-only PR 的链接 / 命令检查 | 人工 | 脚本或 checklist |
| 发布步骤可独立复现 | 无文档 | 1 份清单 |

## 8. 风险

| 风险 | 对策 |
|---|---|
| 文档继续膨胀 | 一份文档一个读者；先合并、再新增 |
| 证据段变成形式 | 必须写 Limitations；评审抽查「没证明什么」 |
| 闸门拖慢 PR | warning 起步；豁免写到到期时间 |
| 设计与实现漂移 | 状态行加基线 commit；实施后改写成当前行为 |
| 规则只是搬家 | 每次合并后用 `grep` 检查同一句式是否还有副本 |
| 文档入库后无人维护 | 每个批次指定 owner；过期状态行在评审中指出 |

| P5 文档闸门 | `scripts/check_docs.py` 检查仓库内链接（含 reference-style）、`:doc:`/`:ref:` 目标、RST 指令与绝对路径、代码块和行内命令中的仓库路径、`cd` 目标、`pip`/`uv` extra 名称；pre-commit 的 `docs-check` hook 严格失败 | 故意制造一条断链，`pre-commit run --all-files` 返回非 0；`tests/unit_tests/scripts/` 覆盖检查器本身 |
